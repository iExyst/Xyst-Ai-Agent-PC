# Cross-channel identity links

The authenticated desktop starts a link with two already-authorized identities from different channels. The owner selects both identities and explicitly chooses which existing session history to share. The other identity's earlier session is retained separately; X.A.A. does not merge its previous conversation into the selected session. The owner can then add one authorized identity from each additional channel to that link. Adding an identity reuses the chosen session and does not merge its older session history.

After linking, both channel bindings point to the selected session. Telegram, Email, and Discord ingress read the binding's session ID before creating a run, so later messages from either linked identity continue the same conversation context. Delivery remains bound to the channel and account that received the message; identity links do not change destinations, credentials, permissions, workspace grants, or run mode.

Unlinking requires a separate confirmation. In one SQLite transaction, X.A.A. creates a new empty session for every binding in the link, clears their link IDs, marks the link revoked, and records an audit event. The old shared session and its messages remain in local history. This prevents future cross-channel context while preserving the conversation record.

Only authorized identities not already linked can be selected, and a link can contain at most one identity per channel. The owner can merge two active groups by choosing the target group's history and explicitly confirming. Every identity in both groups must still be authorized, and the combined groups must have distinct channels. The source group's identities move into the target session; the source link is revoked, and its former session and messages remain in local history without being combined with the target history. Both the target and source audit records identify the merge and retained session. If one member's channel authorization is revoked, the active link remains visible in the desktop, including that member's authorization state, until the owner explicitly unlinks it; groups with revoked members cannot be merged.

The authenticated API exposes `GET /channels/identity-bindings`, `POST /channels/identity-links`, `POST /channels/identity-links/{link_id}/members`, confirmed `POST /channels/identity-links/{link_id}/merge`, and confirmed `DELETE /channels/identity-links/{link_id}`. The merge endpoint uses its path link as the target and `source_link_id` in the request body. The list reveals channel/account identifiers only on the authenticated loopback interface. Storage/API tests verify authorization, cross-channel restrictions, selected-history behavior, membership growth, merge validation, retained history, unlink isolation, schema migration and audit records. Deterministic Telegram, Email and Discord adapter tests verify ingress uses the same session; the desktop browser workflow covers creating, extending, merging and unlinking groups with a mocked API. These checks make no model calls and do not establish live third-party interoperability.
