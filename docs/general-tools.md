# General agent tools

Xyst registers file, process, Git, GitHub, web retrieval, and office-output tools in the same policy-enforced agent loop. Every tool call is persisted and its returned data is treated as untrusted input by the agent.

Only function calls returned through the model API execute tools. If a model prints JSON or a code block that merely describes a tool call, Xyst treats it as text, issues up to two bounded correction turns, and continues only if the model submits an actual tool call. The narrated operation is never replayed or inferred from prose.

## Agent attachments

Attach files to a new task or a resumed session with `xyst agent run --attach path <objective>` and `xyst agent resume <session-id> --attach path <message>`. Repeat `--attach path` to include up to 10 files. Xyst checks each file against the active profile's read roots before opening it. UTF-8 text files are limited to 1 MiB each; PDFs are limited to 20 MiB each and 30,000 extracted characters; PNG, JPEG, and WebP images are limited to 8 MiB each; all attachments together are limited to 20 MiB. Image signatures and PDF signatures are checked before parsing. PDF pages with fewer than 60 selectable characters and a raster image use packaged, offline OCR in the configured English, French, German, and/or Spanish languages, for up to 10 pages at 4 million rendered pixels per page. Configure languages with `xyst config set documents.ocrLanguages '["eng","fra"]' global`; the desktop has the same setting under System settings. Other unsupported binary files and non-UTF-8 text are rejected. Structured attachment messages are stored in the same session journal and sent again when the agent resumes. The desktop composer uses a native file picker for new and resumed tasks. Live direct VLM inference and a full Xyst agent attachment run were verified with Qwen2.5-VL-3B. A direct non-empty answer to a read-only image question can complete without tool evidence when no URL, file output, explicit verification rule, or mission criterion requires it; image edits and mixed requests that require file changes remain evidence-gated.

External actions from GitHub writes, MCP tools, process execution, and workspace mutations are journaled with a stable session or mission-task scope and a normalized argument hash. Repeating the same completed action in that scope returns its saved result instead of issuing it again. `run_process` and workspace mutation actions include the latest other completed Xyst-managed workspace mutation in their idempotency key: after a file, office, browser-download, or Git workspace change, the same action can run against the changed workspace; an unchanged completed action is replayed during recovery. Legacy process results created by older app versions are also reused until a later recorded workspace edit permits a new run. If execution stops after an external action starts but before its outcome is recorded, Xyst marks it uncertain and blocks the affected continuation. Inspect tool calls with `xyst session calls <session-id>` or `xyst mission show <mission-id>`. After checking the external system, use `xyst agent reconcile <session-id> <tool-call-id> completed|retry` or `xyst mission reconcile <mission-id> <run-id> <task-id> <tool-call-id> completed|retry`. `completed` records that the action took effect; `retry` records that it did not and permits a retry. Reconciliation requires the `externalActions` capability.

If the operating system rejects a `run_process` request before creating a process (for example, an executable does not exist), Xyst records a definite failed start and lets the agent correct the executable or arguments. Timeouts and failures after a process has started can leave partial effects and still require reconciliation.

Completion evidence indexes refer to the newest-first list in the current system message. If a response performs file or process actions and calls `task_complete` before a new inference turn, those just-created results were not in the list the model saw. Xyst rejects those stale indexes, shows the refreshed evidence list, and asks the agent to call `task_complete` in the next turn.

## Project instructions

At task start, the agent loads `AGENTS.md` files under the selected workspace, up to eight directory levels, while skipping dependency and build-output folders. Instruction context is capped at 50 files and 50,000 characters. Nested files apply within their directory subtree and take precedence over broader files there. Project instructions cannot expand the active access profile or override the user's task or higher-priority safety rules.

Reusable local guides live at `.xyst/skills/<name>/SKILL.md`. The agent can list and read them through `skill_list` and `skill_read`; skill content is treated as untrusted guidance and is used only when relevant. Skill files are capped at 32 KiB and names are restricted to a single path segment.

## Tool batching

When one model response requests multiple independent file or Git reads, Xyst runs them in bounded parallel batches and stores the returned tool messages in the original call order. Set `tools.maxParallelReads` from 1 to 8 (default 4) to tune the limit; its normal global, project, mission, agent, and session scopes apply. Mutating tools, browser interactions, MCP calls, and other external actions keep the ordered journal and approval flow.

## MCP servers

Configure MCP servers in the desktop Settings → MCP servers JSON editor or with `xyst mcp set servers.json`, inspect saved entries with `xyst mcp list`, and discover live tool schemas with `xyst mcp discover [server-id]`. Enable use by agent tasks in desktop Settings or with `xyst mcp enable on`. Supported transports are local stdio, modern Streamable HTTP, and legacy SSE; HTTP tries Streamable HTTP first and falls back to SSE. Discovered tools use the same agent execution loop, persisted call records, cancellation signal, timeouts, and access policy as built-in tools. When a server advertises resources or prompts, the agent can list and read resources and list and request prompts. Returned MCP content, tool descriptions, and server instructions are untrusted.

All MCP servers require the `integrations` capability. Local stdio servers also require `externalActions` permission and an allowed executable under a restricted profile; remote servers also require `network`. Static bearer tokens and stdio credential environment variables use credential-vault references (`credential set <service> <name>`), never inline secret values. Bearer credentials and OAuth tokens require HTTPS for remote servers; plain HTTP is accepted for loopback development hosts only. For an HTTP server that supports OAuth, set `"oauth": true` in its server definition, then run `xyst mcp auth login <server-id>`, `xyst mcp auth status <server-id>`, or `xyst mcp auth logout <server-id>`. Login uses the system browser and a loopback callback; client registration and tokens are stored in the OS credential vault. OAuth cannot be combined with a static bearer credential. Plain environment variable names that look secret are rejected. Server definitions can scope exposed tools with `allowed_tools`; each server has a bounded timeout and tool count. Servers advertising resource subscriptions expose subscribe, unsubscribe, and recent-update tools. Each server allows up to 50 active subscriptions per agent run and keeps only the latest 50 URI/timestamp notices; a notice contains no resource content, so the agent must explicitly reread the URI. Subscriptions are removed when the run closes. MCP TypeScript client/server SDK 2.4.0 negotiates modern protocol revision 2026-07-28 when available and falls back to legacy 2025-11-25; SSE remains legacy. Resource subscriptions use the negotiated protocol's notification or listen-stream mechanism. During an agent run, Xyst advertises sampling plus `sampling.tools`, routes bounded requests to the selected LM Studio model, and returns any requested tool call to the MCP server without executing it locally. Sampling-enabled connections pin negotiation to legacy 2025-11-25, where sampling tools are defined; normal MCP connections continue automatic modern negotiation. Xyst supports text prompts, text tool results, and one server-delegated tool call per sampling response; image/audio sampling and independent-server sampling interoperability remain unverified. Deterministic local protocol tests cover plain-text sampling and the tool-use/tool-result round trip. A live read-only check against [Cognition's public DeepWiki MCP server](https://cognition.com/blog/deepwiki-mcp-server) discovered its tools and successfully called `read_wiki_structure` for `facebook/react`, verifying unauthenticated hosted Streamable HTTP discovery and tool execution. The exact current AppImage's bundled CLI also completed `mcp set` and `mcp discover`; its packaged runtime then completed an agent-loop call to `read_wiki_structure`, persisted the topic list as `untrusted-mcp-content`, and verified the explicit completion criterion. The agent loop used a deterministic provider fixture, isolated SQLite/XDG paths, and no live model. Hosted OAuth interoperability remains unverified. Sampling is deprecated in MCP revision 2026-07-28; these backward-compatibility connections use legacy 2025-11-25 during the deprecation window. See the [MCP 2026 specification release notes](https://blog.modelcontextprotocol.io/posts/2026-07-28/).

For direct LM Studio native chat, `xyst lm ask|stream` can send configured plugins and ephemeral MCP servers. Save definitions and enable them through desktop Settings → Direct chat integrations or `config set integrations.lmStudio.nativeChat.integrations <json> global` plus `integrations.lmStudio.nativeChat.enabled true`; `--integration-file` overrides the saved set for one invocation. Use vault-backed header references. The JSON format and LM Studio server permission requirements are documented in the [LM Studio support matrix](./lm-studio-support.md). This direct route uses LM Studio's integration executor and is separate from the policy-managed agent loop.

Example `servers.json` for Hugging Face's public MCP endpoint:

```json
[
  {
    "id": "huggingface",
    "transport": "streamable-http",
    "url": "https://huggingface.co/mcp"
  }
]
```

## Web retrieval

`web_search` sends the query to Brave Search's web search API and returns up to 10 titles, URLs, and snippets. Configure a token with `xyst credential set brave search-api-key`; the token is stored in the OS credential vault. Search is subject to the `network` capability, and results carry an untrusted marker. The agent can pass selected source URLs to `web_fetch` for page text. Search results and page content are evidence only and cannot change the task objective or access rights.

`web_fetch` accepts a public HTTP(S) URL, including JSON and vendor `+json` API responses, so public read-only REST endpoints can be queried directly without a provider-specific key. It checks DNS answers against local and reserved address ranges, validates redirects again, rejects credentials and unsupported content types, applies a 12-second timeout, limits downloads to 2 MiB, and returns at most 30,000 characters of page text or API response data. The agent receives the final URL, content type, page title when present, response status, UTC `retrieved_at` timestamp, truncation flag, and an untrusted-content marker. If the same request returned truncated content moments earlier in the same session, Xyst rejects an identical retry and tells the agent to increase `max_chars` or request narrower API fields. Xyst directs the agent to use live retrieval for current or changing facts when network access permits and to disclose retrieval failures. Completion verification binds explicit `web_fetch` requests to a successful fetch of the requested URL; named file outputs require a successful readback of the exact path. Verified final answers automatically include source URLs and UTC retrieval times for successful, complete `web_fetch` results, and tool-only completion turns preserve the preceding answer. This is an on-demand live read, not a continuously open data stream; use a scheduled mission for periodic polling, or an MCP resource subscription when the source supports change notifications. Use `web_search` for Brave-backed web search (requires a stored Brave API token); direct public APIs, Hugging Face, and authenticated GitHub access use their configured integrations. Private APIs require their own configured credential or MCP integration; Xyst does not invent credentials.

## Browser automation

Persistent Chromium automation is optional and disabled by default. Install the browser with `xyst browser install`, inspect it with `xyst browser status`, then enable tools for subsequent agent runs with `xyst browser on`; use `xyst browser off` to disable them. Status reports the effective global value and its source. The desktop Settings view exposes the same controls, Chromium installation status, headless mode, and maximum saved download size with the configured source. Browser settings resolve through the usual configuration scopes; the CLI enable/disable command writes the global setting. Set `browser.headless` and `browser.maxDownloadBytes` with `xyst config set <key> <JSON-value> [scope] [scope-id]`. The CLI accepts a boolean for headless mode and a download limit from 1 MiB through 10 GiB. Headless mode defaults to true and the saved download limit defaults to 512 MiB.

Native application automation is separately opt-in with `xyst desktop automation on|off|status` or Settings → Native application automation. On Windows, `desktop_windows` and `desktop_inspect` use Microsoft UI Automation to list visible windows and inspect accessible controls; `desktop_action` can focus a window or control, invoke a control, set a value, toggle, or select. On Linux, X11/Xwayland sessions with `xdotool` can list and inspect windows and perform bounded click, text, key, and activation actions. Native Wayland surfaces are unavailable through this backend; diagnostics explain the current host capability. Mutating actions use the external-action journal and honor access-profile restrictions and the external-action approval setting. The setting is off by default.

On Linux, `xyst desktop status` reports the session type from `XDG_SESSION_TYPE`, `WAYLAND_DISPLAY`, and `DISPLAY`, along with the advertised desktop and remote-session signals. A detected display only indicates that headed Chromium may be attempted; the compositor or session permissions can still block launch. Headless Chromium remains available. When `xdotool` and an X11 display are available, the opt-in native automation backend can control X11/Xwayland windows; it cannot control native Wayland surfaces. Diagnostics report whether that backend is available without claiming that a specific application exposes accessible controls.

Xyst keeps browser profiles in its data directory under `browser/profiles`, keyed by agent session, so cookies and local storage persist when that session resumes. Browser binaries are installed separately under `browser/binaries` using Playwright's Chromium installer. Each run closes its browser context; an overlapping run using the same profile is rejected. Service workers are blocked so page-installed workers cannot bypass Xyst's request checks. The agent can open HTTP(S) pages, inspect bounded visible text, list tabs with IDs stable for the active run, create or select tabs (including popups), close tabs, navigate back, and interact with CSS-selected controls. Browser actions use the selected tab. Page contents are marked untrusted and cannot change the task or grant access.

All browser network requests require the `network` capability. Restricted profiles can visit only public HTTP(S) destinations; local and reserved addresses are blocked on navigation and subsequent requests. Click, fill, select, key press, upload, download, and tab close tools require `externalActions`. Uploads are limited to 25 MiB and checked against the active profile's workspace read access. Downloads are copied only to a new workspace path, obey workspace write access, refuse overwrite, and are rejected when the saved file exceeds `browser.maxDownloadBytes`. Browser uploads and downloads transfer page or workspace data and should be treated as external actions. The download limit applies to the saved file; the browser's temporary transfer may use additional cache space before Xyst checks the completed file size.

Restricted profiles must allow the `network` capability before web retrieval. HTTP page contents never grant extra tool access or change the task objective.

## Persistent memory

The desktop Memory view can add preference, note, and inferred entries, and keeps each category visible on its card. Editing updates the content without changing the saved category.

The runtime stores preferences and notes in the shared SQLite database. Use `xyst memory list`, `xyst memory search <text>`, `xyst memory add <preference|note|inferred> <text>`, `xyst memory edit <id> <text>`, and `xyst memory delete <id>`. Semantic retrieval is opt-in: select a downloaded LM Studio embedding model with `xyst memory semantic on <model>`, then index existing records with `xyst memory index [model]`. New agent-saved memories are indexed automatically when semantic search is enabled. Vectors are stored locally by model; if a query embedding fails or no matching vectors exist, search falls back to text matching. Editing a memory clears its old vectors until it is indexed again. The desktop Settings view exposes the toggle, model selection, and indexing action. Agent searches may use these entries as user context; agent writes are permitted only after an explicit request to remember something. Credentials and credential-like values are rejected by the storage layer.

## Host resource readings

Run `xyst lm resources` to read total, used, and available RAM on the machine running Xyst. If `nvidia-smi` is available and allowed by the active executable policy, the same command reports current used and free VRAM per NVIDIA device. The Model dock refreshes these readings with its other model state. The data is measured at request time; it does not attribute GPU usage to LM Studio, inspect remote inference hosts, or measure AMD/Apple GPU memory.

## Office artifacts

`office_create` writes new workspace files in these formats:

| Format | Input | Output behavior |
| --- | --- | --- |
| DOCX | Title and text content | Creates a Word document with a title and paragraphs. |
| XLSX | Title and a two-dimensional typed array | Creates one worksheet, styles the header row, freezes it, sizes columns, and adds an autofilter when there is more than one row. Strings, numbers, booleans, and blank cells retain their cell types. Strings beginning with `=` are formulas; Xyst calculates formula caches and returns the calculation summary. |
| CSV | A two-dimensional string array | Quotes and escapes every cell using UTF-8 and CRLF records. |
| PDF | Title and text content | Creates US Letter pages with a title, paragraph spacing, line wrapping, and automatic page breaks using standard Helvetica fonts. |
| PPTX | Titled slide objects with text bodies | Creates a 16:9 dark themed deck with green accent headings. |

For DOCX and PDF creation, `title` becomes the visible heading. If the first nonblank content line exactly matches the title, Xyst removes that duplicate by default; set `repeat_title: true` when a repeated heading is intentional. The document mission template treats its verification task as read-only and asks it to report defects rather than changing the artifact.

The tool requires the matching filename extension, refuses to overwrite an existing file, enforces at most 500,000 characters of structured input, 1,000 spreadsheet rows, and 60 slides. It writes into the agent workspace and checks the active access profile before creating the output. Generation is covered by integrity tests that reopen the PDF and inspect the DOCX/XLSX/PPTX package structure. `office_preview` renders a selected PDF page directly or converts a DOCX, XLSX, or PPTX through an installed LibreOffice command-line renderer before creating a PNG in the workspace. Previews are registered session artifacts and can be opened from the desktop. PDF rendering uses PDF.js and the packaged canvas runtime; page rendering is bounded to 4 million pixels, office conversion to 120 seconds and 50 MiB. LibreOffice is optional, not bundled, and may render layouts differently from Microsoft Office. Set `documents.officeRendererExecutable` if `soffice` is not on PATH. `office_read` extracts bounded main-body text from DOCX files, non-empty cell values from one selected or the first visible XLSX worksheet, quoted CSV fields, slide text from PPTX files, and page text from PDF files. PDF pages with fewer than 60 selectable characters and a raster image use packaged offline OCR using the configured English, French, German, and/or Spanish languages, for up to 10 pages at 4 million rendered pixels per page; each page reports `text`, `ocr`, `empty`, or `ocr_skipped` as its extraction method. CSV fields receive spreadsheet-style addresses and support escaped quotes, embedded commas, and embedded newlines. XLSX reads include formula expressions and stored cached values. `office_edit` uses the returned SHA-256 to replace one unique phrase in the DOCX main body, including phrases split across Word runs, or in PPTX slide text, to set a text cell, set a formula explicitly with `operation: "set_formula"`, append typed rows, or append text to a chosen PDF page. Formula edits trigger workbook cache recalculation. Xyst uses Formualizer's documented XLSX subset, reports calculation errors and unknown functions, and refuses external-workbook links rather than refreshing them. This is not a claim of full Excel equivalence: the evaluator rejects unsupported workbook features, including data tables and some advanced array/spill cases. Recalculation preserves formula text and unrelated package members. PDF text insertion uses standard Helvetica, must fit on the page, and supports WinAnsi text. It adds text over the page content; it does not replace or redact existing PDF text. DOCX and PPTX replacement preserve non-target package parts and existing run formatting. XLSX edits preserve non-target package parts and existing cell style; `set_cell` will not replace a formula, and only the top-left cell of a merged range can be changed. Headers, footers, comments, and images remain unsupported in office_read and office_edit. Office previews use LibreOffice and may differ from Microsoft Office layouts. Use `file_read`/`file_patch` for text, Markdown, JSON, and other supported text files.

## LM Studio structured output

Use `lm json <model> <schema.json> <prompt>` to send a JSON Schema through the documented OpenAI-compatible `response_format: json_schema` interface. The command only accepts a top-level object schema. Output depends on model support; callers must still validate returned JSON against their schema.

The desktop Sessions view includes collapsed execution and artifact records for each selected session. `office_preview` output PNGs appear with `image/png` MIME type and can be opened like other registered artifacts. Expand a tool call to inspect its redacted saved input/output, effect classification, status, and timestamp. Expand an artifact to inspect its registered path, MIME type, and recorded hash metadata. The journals are shared with the CLI through `session calls <id>` and `session artifacts <id>`. Agent-created text files and generated/edited office files are registered automatically after a successful tool call.

When a successful web_fetch response is truncated, Xyst blocks an identical request for two minutes and tells the agent to increase max_chars (up to 30,000) or request narrower fields. Later fresh fetches remain available.

A truncated `web_fetch` result cannot verify task completion. The agent must request more characters or narrower API fields and cite the successful full response instead.

For `task_complete`, the model may provide one evidence index per criterion in the displayed order, a single result only when it supports every criterion, or a shorter set of distinct successful results. For a shorter set, Xyst matches required tool calls, exact requested URLs, and named output paths to the corresponding evidence. Named text files require a successful `file_read` of the exact path; supported office files can use `office_read` for exact-path readback. This reduces index-count errors when several criteria depend on the same fetch or read while preserving the runtime's evidence checks.
