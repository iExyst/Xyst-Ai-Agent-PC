# Configuration reference

Xyst stores versioned settings in its SQLite database, shared by the CLI, desktop, and mission runner. The active value resolves from the most specific available scope in this order:

1. Temporary session
2. Agent
3. Mission
4. Project
5. Global

The stored scope and scope ID are returned with the effective value. A missing setting uses the feature's documented runtime default. Mission definitions can also set per-mission limits and GitHub permissions; those values remain subject to global access policy.

## CLI operations

```sh
xyst config get model.default
xyst config get model.default my-project-id
xyst config get integrations.github.writeEnabled mission <mission-id>
xyst config set browser.headless false global
xyst config set orchestration.maxConcurrency 4 global
xyst config set models.remoteFallbackUrl '"https://inference.example.com"' global
xyst config set models.remoteFallbackModel '"publisher/model-key"' global
xyst credential set lm-studio-remote-fallback api-token
xyst model remote-fallback on
xyst config export
xyst config import settings.json
```

`config get <key> [project-id]` retains the project-ID shorthand. Use `config get <key> <scope> <scope-id> [mission-id]` to resolve the effective value for a session, agent, mission, or project context; agent contexts used by multiple missions can specify the parent mission explicitly. The command follows session → agent → mission → project → global precedence and reports `value`, `source`, and `scopeId`. Mission and agent contexts include their linked project when it can be determined; mission-task sessions also include their parent agent and mission. `config set <key> <JSON-value> [scope] [scope-id]` defaults to global. Boolean and numeric values must be valid JSON (`true`, `false`, `512`, or `null`, without quotes where appropriate).

`config export` returns a JSON object grouped by `scope:scope-id`. Export and import omit an entire setting when its key or a nested object key looks credential-related (token, secret, password, credential, API key, authorization, or cookie), or a string contains a bearer/basic credential, URL user-info, or a credential query parameter. This avoids exporting partial integration objects that could no longer be used safely. Actual credentials belong in the operating system credential vault and are resolved when the feature runs. Import preserves other stored values but does not turn unknown keys into active features; use the table below for settings currently consumed by the runtime. Remove one override with `config reset <key> [scope] [scope-id]`; resolution then uses the next more general scope or the runtime default. `config reset-all [scope] [scope-id]` clears all overrides in that exact scope. The desktop Settings view can reset global overrides; scoped overrides and device-local appearance preferences remain.

## Credential storage

Credentials are stored with the current account's operating-system vault. On Windows, Xyst stores credentials in the current user's Windows credential vault. On Linux, Xyst uses Secret Service on the current user's D-Bus session; a desktop keyring such as GNOME Keyring or another Secret Service implementation must be installed, running, and unlocked. Windows vault write, read, and delete were verified with a disposable entry. Linux Secret Service write, read, and delete were verified with a disposable unlocked GNOME Keyring in an isolated Ubuntu 24.04 WSL D-Bus session; native desktop-session verification remains pending. If Secret Service is unavailable, Xyst reports that requirement and the credential operation fails without storing a plaintext fallback. In unattended Linux service sessions, configure a usable Secret Service session before adding credentials; Xyst does not persist credentials in its SQLite settings database.

Project, mission, agent, and session scopes can override supported keys when the runtime has that context. Desktop Settings contains a **Scoped configuration** editor for every setting listed above: choose its key and scope, load the effective value and source, save a JSON override, or clear it to inherit from the next scope. Agent inspection can include its parent mission; mission-task sessions resolve their linked agent, mission, and project context. The dedicated controls remain available for common global choices, including inference parameters. Leave an inference field blank there to use the LM Studio default. Values with no row here may be stored generically by CLI configuration, but the runtime does not promise they change behavior. See [update feed setup](./updates.md) before enabling desktop updates.

## Desktop appearance preferences

Settings → Appearance stores reduced motion, animation, decorative-effect, robot-presentation, contrast, text-size, accent-color, and sound-alert choices locally on this device. Sound alerts default to off; when enabled, the desktop plays a brief local chime when a mission or background job transitions to completed, succeeded, or failed. The topbar **Panels** menu toggles the left navigation, center work area, right context panel, bottom execution dock, Overview status cards, task composer/activity, model status, recent missions, and runtime status bar. The right panel shows current view, runtime, access profile, model, and selected session; the bottom dock lists saved execution jobs and links to Jobs and Terminal. Panel visibility is saved locally and applies immediately. When navigation is hidden, the topbar shows a page selector so every view remains reachable. These presentation choices do not change runtime or CLI behavior.

## Restricted filesystem paths

Restricted profiles resolve symlinks and Windows junctions to the canonical target before checking the configured read or write roots. File operations use that resolved target after the check, including when one restricted profile delegates to another. New paths resolve the nearest existing ancestor and append the remaining path segments before applying the same root rule. Windows 11 checks cover junctions that stay inside and escape an allowed root, plus atomic create/read/patch operations on paths longer than 260 characters. Ubuntu 24.04 WSL checks cover in-root and out-of-root symbolic links. Native Linux distribution behavior still needs host verification; see [platform support](./platform-support.md).
