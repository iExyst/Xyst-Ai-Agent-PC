## Initial upstream inventory

Pinned README advertises six messaging gateway families in its quick reference (Telegram, Discord, Slack, WhatsApp, Signal, Email), and its documentation table additionally names Home Assistant. It advertises six built-in terminal backends: local, Docker, SSH, Modal, Daytona, Vercel Sandbox; it also names plugin backends such as Singularity/Apptainer. These are README-level inventory leads only. Exact supported adapters, version-specific limits, and feature behavior still require source-level inspection of `gateway/`, `plugins/`, `tools/`, `providers/`, `cron/`, `hermes_cli/` and official docs before parity scope is frozen.

## Backlog policy

Source inventory follow-up: `pinned-inventory.json` records all 27 in-tree platform manifests with their declared configuration variable names, version, phase and acceptance requirement. Core gateway transports are `api_server`, `webhook` and `msgraph_webhook`. `execution-inventory.json` now verifies the six built-in factory families and seven reserved names against parsed source declarations; managed_modal is an internal mode. It also records eight external backend catalog declarations with repository pins, dependencies, platform declarations and candidate exclusions. `execution-requirements.md` defines shared and backend-specific acceptance gates and implementation phases. External source/runtime inspection and complete catalog discovery remain open; catalog descriptions do not establish supported behavior or parity. This replaces the README-only backend inventory as the working scope baseline.

Channel source follow-up: `channel-inventory.json` identifies WeCom's second registration (`wecom_callback`) and separates declarations from actual media/runtime support. `channel-requirements.md` covers all 31 inspected in-tree/core routes and defines separate service/topic trust boundaries. It resolves the Home Assistant README lead to an externally pinned official catalog plugin and records platform-category discovery candidates without counting them all as supported channels. External source inspection and full registration/mixin behavior remain open.

The pinned commit is the audit target. Any feature first added upstream after this pin belongs in a separately dated upstream-delta backlog, not in the pinned parity verdict.
