# Execution backend acceptance requirements

Reference: Hermes commit `1e208b280deb18f01d015b0acdf3ef3552d08039`, audited 2026-11-03. `execution-inventory.json` records source hashes, class line numbers, factory names, external repository pins and discovery limits. Run `uv run python scripts/audit_execution_inventory.py --check` to detect drift against the pinned checkout. The script parses source syntax and safe YAML; it does not import upstream modules, install plugins or execute their code.

The audit checkout is a development-only input, excluded from the X.A.A. package. To reproduce from a checkout without it, run the following from the repository root; an existing `.hermes-audit` directory must be inspected rather than overwritten:

```powershell
git clone --filter=blob:none --no-checkout https://github.com/NousResearch/hermes-agent .hermes-audit
git -C .hermes-audit checkout --detach 1e208b280deb18f01d015b0acdf3ef3552d08039
uv run python scripts/audit_execution_inventory.py --check
```

The factory defines six built-in families: local, Docker, SSH, Modal, Daytona and Vercel Sandbox. The registry also reserves `managed_modal`; the Modal builder selects that internal mode through gateway configuration. It is not a seventh independent factory backend. The inspected base contract describes per-call shell processes, session-state snapshots, persisted working directories and process cleanup. Source inspection here covers declarations and selected requirement/lifecycle paths, not every implementation branch. X.A.A. must implement its own execution code and pass observable acceptance tests; a compatible interface does not establish parity.

X.A.A. has a Windows-first WSL/Bubblewrap restricted command backend with durable grants, isolated project snapshots, output artifacts, cancellation/recovery handling, and native installed-package acceptance. This is a partial X.A.A.-owned backend implementation; it does not establish support for the six Hermes built-in execution families, external plugins, or all shared release requirements below. The fixed Git inspector and filesystem workers remain separate supporting application operations.

## Requirements shared by every claimed backend

| ID | Observable acceptance requirement | Required evidence |
|---|---|---|
| EXEC-COMMON-1 | An explicitly configured backend runs a fixture command in the declared workspace. UI/API identifies the actual environment, working directory, execution ID and exit status. Unavailable selection produces an actionable error without changing backend. | Real environment identity, captured command/argument boundaries, stdout/stderr, exit code and durable event records. |
| EXEC-COMMON-2 | Generated code cannot read or modify sentinel files outside its granted workspace, access the engine API credential, or expand its own permissions. Network access follows its explicit grant. | Positive workspace operations plus denied host/credential/network probes on the actual backend. A timeout or separate process alone cannot pass this requirement. |
| EXEC-COMMON-3 | Required wall-time, output, memory, CPU, process and storage limits are enforced or the operation is refused before execution. Unsupported controls are reported accurately. | Actual limit probes and measured outcomes. Upstream Docker gates some resource flags on a capability probe; that behavior is not evidence that every host enforces them. |
| EXEC-COMMON-4 | Pause/cancel/emergency stop terminate the owned command tree or report unresolved remote execution. A crash after a possible write requires destination reconciliation before repetition. | Real long-running child/descendant interruption, service restart and write-boundary kill tests with unchanged unrelated work. |
| EXEC-COMMON-5 | Unicode stdout/stderr and exit status survive transport; excerpts stay bounded and complete outputs become inspectable hashed artifacts. Model text is never promoted to an executable command outside a validated tool proposal. | Large/fragmented output, malformed responses, argument-boundary probes, artifact hashes and transcript inspection. |
| EXEC-COMMON-6 | Independent coding tasks have isolated workspaces. Persistence/restart retains only the intended task's files; integration resolves conflicts and runs project validation. Nonpersistent cleanup does not delete another task's workspace. | Two concurrent task fixtures, restart/reconnect, conflicting edits, successful merged validation and teardown evidence. |
| EXEC-COMMON-7 | Credentials stay in the OS store and narrowly scoped transport. Host homes, skill caches and credential files are not uploaded or mounted implicitly. Cloud execution requires explicit configuration and destination authorization. | Credential/environment sentinel probes, redacted exports/logs, inspected mount/upload manifests and permission decisions. |
| EXEC-COMMON-8 | Health checks distinguish missing executable/SDK, unavailable service, rejected authentication and unsupported configuration. Setup cannot silently provision a billable resource or fall back to unrestricted host execution. | Real dependency/authentication failures, unreachable service, cleanup failures and selected-backend persistence tests. |

These are X.A.A. release requirements. Catalog descriptions sometimes declare credential uploads or reduced approval behavior; that does not authorize X.A.A. to copy those policies.

## External catalog declarations

Eight declarations were identified after inspecting 25 keyword candidates across the pinned catalog. Seventeen related-feature matches were excluded with recorded reasons. Search uses description text containing `terminal` and either `backend` or `environment`; this is a discovery aid, not proof that every external capability has been found. The first narrower phrase search missed both Windows entries, demonstrating that limitation.

The inventory records each catalog's external repository SHA and subdirectory. All eight external backend declarations have pinned-source reviews, but no external backend was installed or executed. Empty platform lists do not establish Windows support. Every external row remains **planned**, Phase 9, and requires the shared contract and its scenario below. See [`external-plugin-source-audit.md`](external-plugin-source-audit.md) for source observations and limits.

| Declaration | Catalog-described behavior/constraint | Acceptance scenario still required |
|---|---|---|
| bubblewrap | Linux bwrap/prlimit profiles; writable host workspace with profile-dependent network behavior. | Source reviewed: the default profile shares host networking, other profiles use loopback only, limits are per-process rlimits, selected credentials/sockets are masked, and other host-readable files/sockets can remain reachable. Probe every relevant boundary and effective resource control. |
| cua-spaces | Local, cloud or host Space; supports multiple Space operating systems, with provider-dependent stream behavior. | Source reviewed: creation/deletion and existing-Space ownership differ; inspect file/credential transfers, network/resources, per-OS cancellation and cleanup; verify target identity and EXEC-COMMON-1 through EXEC-COMMON-8. |
| deepinfra-sandbox | Billable remote sandbox; plugin syncs Hermes skill/cache and registered credential files. | Source reviewed: generic CPU/memory settings are not mapped, image is fixed, interruption stops the whole sandbox and only `/workspace` persists; verify plan billing, actual isolation/network, transfer manifest and cleanup. |
| singularity | Linux Apptainer/Singularity container and optional persistent overlay. | Source reviewed: `--containall --no-home`, optional read-only credential/skill mounts, CPU/memory flags and per-process overlay cleanup; the configured disk value only drives an advisory warning, and no explicit network-denial policy was found. Still verify real containment, limits, overlay isolation and teardown. |
| smolmachines | Local microVM on supported macOS/Linux hosts with guest networking enabled. | Source reviewed: CPU/memory pass into VM config and persistent VMs are left running; inspect host Docker registry credentials, effective microVM boundary, network, output limits and cleanup. |
| upstash-box | Named/persistent or ephemeral cloud containers; Hermes files sync and account-connected credentials may be present in the guest. | Source reviewed: account credentials/files and cross-profile name collisions are relevant; verify explicit transfer policy, fixed resource behavior, billing, pause/delete, stream interruption and crash cleanup. |
| hermes-wsl-terminal | Existing WSL distro, translated host paths, full access as the configured user; explicitly not a sandbox. | Source reviewed: verify routing/CWD/exit transport only. It cannot enable X.A.A. generated-code execution or bypass the restricted WSL/Bubblewrap boundary. |
| hermes-wslc-sandbox | Windows WSL Containers sandbox with optional persistence and configurable network/volumes. | Source reviewed: runtime rejects capability/security/PID/init/storage flags; disk is not enforced, networking defaults on, and persistent writable layers survive environment teardown. Measure actual limits and cross-task isolation on a real host; refuse requirements the runtime cannot enforce. |

The current host has `wsl.exe`, an Ubuntu-24.04 WSL distribution and Bubblewrap 0.9.0 with namespace and cgroup-v2 support; actual restricted probes and native installed command/project-fix acceptance are recorded in `../architecture/wsl-sandbox-probes.md`, `../architecture/wsl-executor.md`, and `.acceptance/installed-command-16dc8efdd5b840699cdb7514220049a2/`. Windows PATH has no `docker`, `podman`, `wslc`, `bwrap` or `apptainer` executable, and no restricted SSH host or cloud execution account is configured. These environment gaps leave the other direct backends unverified; they do not negate the X.A.A.-owned WSL/Bubblewrap slice.

Phase 0's eight external execution backend source reviews are complete; broader catalog discovery, channel-specific behavior and other capability families remain open. The reviews in `external-plugin-source-audit.md` do not establish runtime parity. The Phase 3 acceptance scenario has now passed on both a native development Tauri build and an isolated installed Windows package: the granted WSL/Bubblewrap command path repaired a five-case fixture, ran its unchanged checks, surfaced the exact command output, and verified that tested snapshot bytes match the retained correction. Evidence: [`native-project-fix.json`](../releases/evidence/native-project-fix.json) and the installed report under [`.acceptance/installed-command-16dc8efdd5b840699cdb7514220049a2/`](../../.acceptance/installed-command-16dc8efdd5b840699cdb7514220049a2/). The installed fixture used an automated reviewer and is not clean-machine, upgrade, reboot, or human-review acceptance. The 0.1.1 package independently passed install/upgrade/boot/uninstall and frozen execution-scope acceptance in [run 43162210451](https://github.com/iExyst/Xyst-Ai-Agent-PC/actions/runs/43162210451); that CI run did not repeat live-model execution. Saved WSL control requests now tolerate a packaged profile-fingerprint change when they target the journaled execution ID in its original distribution; fresh launches remain fingerprint-gated. This source regression does not yet prove installed-package upgrade recovery or historical manager-schema compatibility. Phase 3's narrow gate is demonstrated, while broad project/runtime support, cross-backend parity, and wider recovery remain open.
