# Pinned external plugin source audit

Reviewed 2026-11-06 against the exact catalog pins recorded by the Hermes audit. This is source review only. No upstream plugin was installed, imported, or executed; no external runtime acceptance is claimed.

## Home Assistant gateway and tools

Reference: `NousResearch/hermes-official-plugins` commit `4d492b1dc5326af3e38bb2cf3e4b9ad6d65f0072`, subdirectory `homeassistant`, catalog version 2.0.1. Reviewed `homeassistant/__init__.py`, `adapter.py`, `tools.py`, and `README.md`.

- The public plugin entry point registers one gateway platform and four tools: `ha_list_entities`, `ha_get_state`, `ha_list_services`, and `ha_call_service`. The platform is marked `trusted_inbound=True` when the running core supports that field. The source rationale is that events are generated by the authenticated Home Assistant instance, not a human identity.
- `HASS_TOKEN` is required. `HASS_URL` defaults to `http://homeassistant.local:8123`. The scheme validator accepts both HTTP and HTTPS, and the WebSocket derives `ws://` for HTTP, so bearer credentials may be transmitted without transport encryption. X.A.A. must default to verified HTTPS and clearly gate any local cleartext exception.
- Event intake subscribes to WebSocket `state_changed`, defaults to closed behavior until `watch_domains`, `watch_entities`, or `watch_all` is configured, supports ignored entities and a default 30-second per-entity cooldown, and reconnects with 5/10/30/60-second backoff. Its event identity uses entity plus integer wall time; the source contains no durable cursor/replay store. State names and attributes are external data and must remain untrusted.
- Normal gateway replies use Home Assistant persistent notifications. Scheduled delivery can target `notify.<target>` without a running gateway. The plugin has no service-side authorization model for individual users.
- Tool-side entity allow/deny lists are optional. If absent, entity reads and service targets are not constrained by those lists. When a list is configured, the plugin blocks indirect area/device/floor/label targets, `all`, and targetless services because it cannot validate their resolved entities. A blocklist rejects `shell_command`, `command_line`, `python_script`, `pyscript`, `hassio`, and `rest_command`; names and entity paths receive syntax validation.
- The source documentation explicitly says Home Assistant has no service-level access control and recommends a restricted Home Assistant identity. X.A.A. therefore needs its own explicit per-run write grant, target allowlist, target-resolution restrictions, and untrusted-output handling; optional upstream filters are not an adequate permission boundary.

Acceptance still required: transport encryption/identity checks against a configured HA instance; event replay/reconnect and durable deduplication; bounded untrusted event handling; entity filtering; notification reconciliation after ambiguous delivery; tool read/write grants and denial probes. Do not infer exactly-once delivery from the upstream adapter.

## Singularity/Apptainer execution backend

Reference: `NousResearch/hermes-official-plugins` commit `d46aced3031a8f533fdbf0806bc4cf0d0b28be07`, subdirectory `singularity`, catalog version 1.0.0. Reviewed `singularity/provider.py`, `singularity/singularity_env.py`, and `singularity/README.md`.

- The catalog and provider restrict support to Linux and discover `apptainer` or `singularity` from PATH. The environment checks the executable version and resolves a configured image; a Docker image reference may trigger a SIF build and cache.
- Startup uses `instance start --containall --no-home`, adds either a writable per-task overlay or writable tmpfs, and mounts registered credential files and skills read-only when those mount providers load successfully. It passes optional `--memory` and `--cpus` flags. The configured disk value is consumed by an advisory scratch usage warning; source does not establish an enforced disk quota.
- Commands execute through `exec instance://... bash -c ...`. The source does not add a network-denial or explicit egress policy, so network isolation must not be inferred from `--containall` or the README's “hardened” description. Execution is rootless as the caller, not a separate identity. Process exit cleanup stops the instance and sweeps scratch directories; persistent overlays last until the Hermes process exits.
- The upstream README and tests describe intended behavior, but no real Apptainer runtime, image, host policy, escaping, effective CPU/memory limits, network boundary, or crash cleanup was exercised in this audit.

Acceptance still required: inspect effective mount/user/network namespaces and host/credential access on each supported host; prove CPU/memory/PID/storage limits; test command-tree cancellation, crash/restart and overlay isolation/retention; inspect image acquisition and bind manifests; reject unsupported controls. These are backend-specific additions to `EXEC-COMMON-1` through `EXEC-COMMON-8`.
