# Channel and gateway transport requirements

Reference: Hermes `1e208b280deb18f01d015b0acdf3ef3552d08039`, audit date 2026-11-03. `channel-inventory.json` records 27 in-tree platform manifests, **28 registered adapter names**, and three additional core gateway transports. WeCom registers both `wecom` and `wecom_callback`; they require separate transport and security tests. A manifest count is not an adapter count.

Run `uv run python scripts/audit_channel_inventory.py --check` from the repository root with the pinned `.hermes-audit` checkout described in `execution-requirements.md`. The script verifies the clean reference pin, enumerates tracked sources, parses registration calls and adapter declarations without importing them, and checks the generated inventory for drift. It records source hashes, registration/class locations, factory expressions and declared environment-variable names. No credentials are read and no messages are sent.

This is source-declaration and selected-path evidence. A declared method may delegate to a mixin, inherit an unsupported fallback or reject a media type. Method names and manifest claims do not prove runtime support. X.A.A. currently has text-only Telegram and Email adapters, a private-DM-only Discord inbound adapter, and signed text-only generic webhook ingress. The Discord adapter queues paired DM text into Observe-mode runs and has no outbound replies yet (see [`discord.md`](../channels/discord.md)). Fixture coverage exercises authorization, deduplication, delivery and recovery for selected paths; live external interoperability remains unverified. The generic webhook establishes a shared-key sender boundary, creates isolated Observe-mode runs, and has no outbound messaging. All other channel-specific rows are planned for their future `engine/xaa/channels/<adapter>` modules. Phase 9 covers the remaining inventoried channels and advanced/media behavior, including full parity for Telegram, Email and generic webhook callbacks.

## Source coverage and remaining work

Registration code and adapter declarations were read without starting any adapter or installing an upstream SDK. Discord and other channels delegate behavior to mixins; these need method-level inspection before media/voice/authorization claims can be frozen. The source registration and dashboard descriptions can also differ (for example WeCom), so descriptive picker text is not sufficient evidence.

X.A.A. now has a first text-only Telegram adapter at `engine/xaa/channels/telegram.py`; its credential, private pairing, per-bot status, explicit linked-user revocation, update deduplication and delivery status behavior are described in `../channels/telegram.md`. Automated fixture acceptance covers the shared-coordinator path, but no real Telegram bot, configured test chat or authorized external delivery has been established. No external message was sent. Live Phase 8 acceptance still requires a deliberately configured test bot and private account; the fixture is not evidence of external interoperability.

The README's Home Assistant reference points to the external official catalog plugin at repository `NousResearch/hermes-official-plugins`, commit `4d492b1dc5326af3e38bb2cf3e4b9ad6d65f0072`, subdirectory `homeassistant`, version 2.0.1. Its source has now been reviewed: it registers state-change ingress, persistent/cron notification delivery and four entity/service tools with `HASS_TOKEN`; inbound events are trusted as service-generated, optional entity lists do not constrain tools when unset, and HTTP URLs are accepted. Acceptance must verify transport and service identity, permitted entities, durable event deduplication, notification reconciliation, and a separate explicit grant for service actions. See [`external-plugin-source-audit.md`](external-plugin-source-audit.md). Runtime acceptance remains open; the plugin is not counted as an in-tree registration.

All 976 tracked catalog manifests were also scanned for category `platform`, producing 49 discovery candidates with repository pins and configuration declarations. This category includes non-channel features: DeepInfra sandbox is an execution backend, discord-tps is a presence hook, and render-platform provides deployment MCP/skills. Those exclusions are explicit; other candidates still need individual source classification. Other catalog categories may also register channels, so the category scan is not exhaustive ecosystem coverage.

The 31 rows above describe inspected in-tree registrations/core transports. External catalog candidates are recorded separately in `channel-inventory.json`. All 49 platform-category candidates are now classified: 46 have pinned static source reviews (39 messaging/gateway declarations, six source-reviewed non-channel plugins, and the Home Assistant gateway/toolset); three additional exclusions retain catalog-derived classifications without source review. No platform-category candidate remains unclassified. These reviews do not establish plugin runtime behavior. Broader discovery outside this catalog category, deeper method/mixin behavior, runtime acceptance, and the other capability families remain open.
