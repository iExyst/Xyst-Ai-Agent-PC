# Restricted WSL command executor development slice

`engine/xaa/runtime/wsl_manager.py` is a standard-library Linux-side manager for one command in an explicitly selected existing WSL distro. `sandbox_profile.py` constructs the fixed execution profile. The source diagnostic launches the manager with Python isolated mode (`-I`); the manager clears its own environment and passes only PATH/LANG onward. Codec/profile source paths come from application code, not command arguments proposed by a model. The manager accepts bounded JSON stdin and never treats project content or argument strings as host-side Python/shell source.

The command has 1..64 structured arguments, a 16 KiB aggregate argument limit and an application-generated lowercase UUID identity. Requests cannot alter profile mounts, network access, environment or resources; unknown/duplicate fields and invalid types/limits are rejected. The selected Linux host needs root service-management access, Bubblewrap, Python 3, systemd with memory/cpu/pids controllers and libseccomp. Missing requirements fail; direct host execution is not a fallback. No software or distro setting is installed/changed by the diagnostic.

The manager validates the bounded snapshot, materializes it under private root-owned `/tmp/xaa-executions/<id>/input`, then launches a uniquely named systemd unit. Bubblewrap provides separate user/mount/process/network/IPC/UTS/cgroup namespaces, no capabilities, no-new-privileges, disabled further user namespaces, read-only runtime/root/dev/input mounts and separate 32 MiB scratch/workspace tmpfs mounts. A fixed isolated Python bootstrap copies the regular-file input snapshot into the private writable workspace, then calls execvpe with the decoded argument array. Workspace writes are ephemeral; original Windows files are never mounted or modified by the command.

The profile enforces 128 MiB aggregate memory, no swap, half-CPU quota, 32 tasks, 1..30 seconds of runtime and a combined 1 MiB stdout/stderr capture limit. On capture overflow the manager stops its exact owned unit rather than reading indefinitely. Captured bytes use base64 transport and remain untrusted. systemd status is obtained separately from the command output; model-controlled log text is not parsed as authoritative unit state.

A native-architecture libseccomp BPF filter is supplied to Bubblewrap through its stdin descriptor and applied to the child after namespace setup. The profile rejects mount/namespace/ptrace/process-memory/keyring/kernel-management/handle-based filesystem/io_uring calls. clone3 returns ENOSYS to permit libc's ordinary process-creation fallback. Socket creation/use is denied, including Unix and VM/VSOCK families; commands needing sockets are unsupported by this profile even for local test IPC. Missing syscall definitions/export failures reject launch. This is a concrete tested policy, not a claim of complete kernel escape resistance or an exhaustive security audit.

## Results and cancellation

The supervised process exit status and command outcome are separate. `exit_code` is available on normal termination; stopped/timed-out/OOM/truncated/cancelled operations use null, `succeeded=false` and an explicit termination reason. `supervisor_exit_code` is retained because systemd can consider explicit SIGTERM cleanup a successful service stop. It must not be used as a successful project-validation result by itself.

A trusted stop request writes/fsyncs a cancellation receipt outside sandbox-visible mounts before stopping the unit. The active manager preserves that cancellation reason when collecting the result. A stop acknowledgment identifies unit shutdown; staging cleanup is a separate operation. Final cleanup stops/resets only the exact UUID unit, confirms inactive state and removes only its private checked staging directory. Persistent identity and closure records are retained. An existing staging destination is refused rather than overwritten.

This source slice now fences Linux execution identities with private persistent receipts; the follow-up below verifies stop-before-launch, delayed-job conditions, duplicate/concurrent requests and manager-process death. It does not yet bind those identities to durable Windows run/tool leases. Windows worker/supervisor cancellation, engine crash/recovery, profile grants and artifact ownership still require the controller/journal handshake and adversarial acceptance. No application/model tool is exposed until those controls, per-run explicit grants, packaged manager resources, artifact registration and end-to-end model/native acceptance are integrated. A passed development diagnostic is not the completed Phase 3 gate.

## Actual acceptance

Run `uv run python scripts/wsl_executor_diagnostic.py --distribution Ubuntu-24.04`. Evidence `.acceptance/564029d7-dd0b-4d0e-a37a-740406934669/` and `../releases/evidence/wsl-executor.json` covers:

- A small Python fixture's unittest fails with the defect (exit 1), then passes after an explicitly automated diagnostic patch (exit 0). The patch actor is the diagnostic, not a local model; this is not autonomous defect-repair acceptance.
- The command changes its private copy while the original snapshot/Windows fixture remain unchanged. Literal shell punctuation and Unicode travel as a single argument.
- Seccomp is active, clone3 receives ENOSYS and nested namespace creation plus IPv4/Unix/VM socket creation are denied.
- A million-byte output flood is bounded/stopped; a sleeping parent/child hit the one-second runtime limit; a 256 MiB allocation is killed under the 128 MiB memory cap; both writable mounts hit ENOSPC; task creation hits EAGAIN; explicit exit 7 is preserved.
- Cancellation occurs only after observing two actual Python workload PIDs in the exact unit cgroup. The result retains cancellation, every accepted operation confirms owned-unit/staging cleanup, and original project bytes remain unchanged.

Fourteen negative unit cases reject malformed identities, argument types/NUL/size, runtime escalation, invalid snapshot encoding, unauthorized network fields, duplicate/oversized envelopes and missing libseccomp without falling back. Complete engine suite: 323 passed with the existing Starlette/httpx deprecation warning. Full Ruff/format and strict engine/scripts typing pass.

Failed diagnostic runs remain separately retained: `.acceptance/49d5bb18-497f-4b71-bf43-96d8301d6a28/` exposed failed-unit cleanup; reset-failed was added before checking inactive state. Subsequent early cancellation fixtures either ran before the workload was observed or lacked the intended child. They were not counted as cancellation passes; the final fixture observes both actual processes and uses a trusted cancellation receipt so a clean service-stop status cannot be mistaken for command success.

## Persistent identity and closure follow-up

`execution_receipts.py` maintains a private root-owned `/var/lib/xaa-execution-manager` directory with a canonical version-1 schema. A bounded admission registry retains at most 4096 identities; existing identities can still be controlled at capacity. Global admission and per-identity flock locks serialize publication and execution ownership. A claim is published exclusively before any unit launch. Duplicate claims never enter the command path, and a failed duplicate request never cleans up the original owner's workload.

Metadata records are written/fsynced to private temporary regular files, published with an exclusive hard link, and directory-fsynced. Parent directory creation is also synced. Claim records retain a request digest plus manager PID, process start-time and Linux boot ID. Outcomes retain bounded metadata and output hashes/counts; raw command output remains a caller-owned artifact, not duplicated into backend receipts. A schema change or non-private root fails closed. Symlink closure markers are rejected. Receipt reads expose whether that exact manager identity remains alive; PID numbers alone are not treated as ownership.

Stop and cleanup permanently seal the identity. Each systemd unit has an application-selected `ConditionPathExists=!<identity>.closed` start condition, so a job that arrives after closure cannot execute even if the stop initially found no loaded unit. Cleanup never removes the claim/closure fence. A stop-before-launch request consumes and closes the identity; late run requests fail. A completed identity cannot be reused for another command, snapshot or profile. Retention exhaustion refuses new work; a coordinated retention/maintenance policy is not yet implemented and receipt deletion is not presented as a recovery shortcut.

Finalization and stop are serialized by identity. Cancellation remains distinct from a service supervisor's clean stop. After a killed manager, a fresh controller can seal the known identity, stop its exact unit and remove its private staging; an absent outcome remains absent. Neither successful cleanup nor a dead manager invents a successful command result. The caller must reconcile the Windows journal instead of automatically replaying the command.

Actual evidence `.acceptance/29dd457a-3cad-4376-9755-67a81db7836b/` and `../releases/evidence/wsl-execution-receipts.json` reruns every preceding execution/resource case and adds:

- Completed-request replay is refused with its original receipt unchanged.
- Stop followed by cleanup before launch still refuses execution. A deliberately delayed direct systemd fixture using the same start condition produces no command output.
- Two concurrent managers for one identity yield exactly one winner. The losing claim cannot terminate or overwrite the winner's operation.
- The test observes two workload processes, verifies the manager PID/start-time/boot ID, kills that manager with SIGKILL, then recovers through a fresh process. Replay is rejected before and after cleanup, staging/unit cleanup succeeds, the claim survives and no outcome is fabricated.
- Separate private Linux fixtures prove full-admission refusal with existing-identity control still allowed, marker-symlink rejection, non-private-root rejection, and refusal of an unknown schema without rewriting it.

This verifies manager-process persistence and recovery on the actual selected distro. It does not test a whole WSL/Windows reboot or power failure. Product tool access remains disabled pending explicit per-run profile permission, authoritative Windows tool-intent/lease binding, snapshot capture in an owned bounded worker, protected application-state path policy, global command-resource admission, artifact registration, frozen resource packaging, engine startup/cancel/crash recovery and real model/native defect-patch-validation acceptance. The Phase 3 and full-release gates remain incomplete.


## Windows journal and lease integration (2026-11-04)

The internal RunStore create-run transaction can now save an explicit local-user command grant with a fixed backend, distribution, profile digest and duration ceiling. HTTP run creation and the model catalog do not expose this grant yet. The selected canonical project must be separate from live engine/runtime and application data. Command arguments cannot supply authority fields.

CommandJournal reserves a generated execution identity and tool intent in one SQLite transaction before transport. It binds snapshot registration and launch authorization to the original live lease, the saved grant and an exact registered canonical manifest. A replacement lease must reconcile the identity rather than launch it. At most two unresolved commands are admitted per engine database; paused or crashed operations retain their slots until cleanup is proved. This is not yet admission across multiple engine databases.

Completion requires matching run-owned stdout/stderr artifacts, provenance, hashes, byte bounds, snapshot and execution identity. The journal reads bounded output itself and marks excerpts as untrusted. A fresh lease may commit a known sealed result without re-executing it. Missing results require sealed, stopped-unit, dead-manager cleanup evidence and remain explicitly not_verified with no invented exit status. Cancellation cleanup can use an exact stopped-run revision after the worker lease has been revoked; it cannot advance state or succeed after resume changes the revision. These evidence entry points are controller internals, not HTTP or model assertions.

Pause, block, failure, cancellation and approval waits now revoke the lease token transactionally. Requeue also clears legacy retained tokens, preventing stop/resume from reviving an old worker. Regression tests cover that authority change.

Actual development evidence in ../releases/evidence/windows-command-journal.json verifies known-result recovery after lease replacement, interrupted prelaunch recovery without replay, manager SIGKILL after observing parent and child workload processes, and cleanup after run cancellation. The original project is unchanged and no commands remain unresolved. The fault actor is an automated diagnostic, not a model. Reproduce with uv run python scripts/command_journal_diagnostic.py --distribution Ubuntu-24.04.

The systemd ExecStartPre gate now checks actual per-unit memory, swap, process and CPU controls. The isolated bootstrap checks effective UID/GID, capabilities, no-new-privileges, seccomp and tmpfs sizes before copying input or executing project code. All existing real resource/replay/crash probes pass again; see ../releases/evidence/wsl-executor-cgroup-gate.json. Negative gate configuration and unusual resource-path acceptance still need dedicated coverage.

Before product exposure, remaining integration includes an owned bounded snapshot/transport controller, remaining parent-wall-budget enforcement, authoritative profile fingerprint discovery, cross-engine admission policy, live-runtime and private-state mutation protection for all file tools, packaging the trusted resources, startup/cancel/reboot recovery, explicit UI grants and real model/native validation. Existing file tools now reject hardlinked edits, Git discovery ignores relative/project PATH entries and Windows batch wrappers, and source workers use isolated Python imports; these guards do not complete the broader protected-path policy.

Protected mutation follow-up: WorkspaceExecutor now supplies its actual database to handle-level guards for creation, editing, patches/replacements and reconciliation. Live engine/desktop/runtime and database/artifact/backup/WSL-private destinations are reserved, including resolved directory aliases. See workspace-mutation-policy.md for verification scope and the remaining packaged acceptance gap. This supersedes the file-tool policy item above only; controller and product command acceptance remain unfinished.
