# Fixed execution-readiness checks

POST /execution/readiness accepts only a selected distribution name and requires the normal loopback bearer authentication. It never accepts argv, project paths, environment, mounts or a client-supplied profile hash. It does not create a run or grant execution permission. The returned profile fingerprint and policy describe the application-selected restricted backend, rather than client authority.

The explicit request runs a fixed application-owned Python self-test with a fresh nonce snapshot, no selected project and a five-second command limit. The normal trusted systemd/Bubblewrap/seccomp path is used. It checks UID/GID 65534, no effective capabilities, no-new-privileges, active seccomp, read-only root/runtime/input, bounded private tmpfs, absence of host mounts, an exact credential-free environment, IPv4/IPv6/Unix/VSOCK socket denial and nested-user-namespace denial. The trusted per-unit cgroup gate must pass before the fixed script starts. The result must match its nonce/snapshot and the declared backend/resource policy. Successful output alone is insufficient: separate cleanup/status must confirm a sealed identity and a dead manager before readiness is returned.

One probe can run at a time per engine; additional uncached requests return busy instead of queuing. Success is cached for sixty seconds, failures for ten, with at most eight current distribution entries. Every lookup recomputes the resource fingerprint so changed/missing resources cannot reuse a previous ready result. Unsupported platforms do not launch WSL. Exceptions expose a bounded error code, not raw manager stderr or credentials. Cancellation retains cleanup ownership, including repeated cancellation, and does not cache readiness.

The first calibration rejected Bubblewrap's PWD variable. The final exact allowlist includes PWD only when its value is /workspace. No host environment or credential value is copied into the response. A missing distro, unavailable controls, malformed nonce/boolean, altered declared limits or unconfirmed cleanup produces unavailable with no passed-check list. Missing prerequisites never trigger direct host execution or software installation.

The response includes immutable policy limits and checked/expiry timestamps. Ready means that this fixed self-test passed at that time. It does not prove arbitrary project dependencies, grant project permissions, bypass the per-run grant boundary or establish full backend parity. Global admission across engine processes and receipt-retention maintenance remain separate requirements. Self-tests use the existing persistent identity/closure mechanism; they do not erase receipts to reset quota.
