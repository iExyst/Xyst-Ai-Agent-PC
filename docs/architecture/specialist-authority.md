# Specialist filesystem authority

Specialist workers carry the saved task ID and opaque worker token in the private worker protocol. Model tool arguments cannot select that scope, a root directory, parent ownership or an operating mode. Both scope fields must be present together. Ordinary scoped filesystem requests permit only internal read/list operations; dedicated private workspace operations additionally require the task's saved workspace.write permission.

A scoped RunStore validates the current parent lease and exact running task/token/expiry, workspace.read permission and saved task-to-parent workspace binding. The same validation applies at filesystem intent and result transactions, not just in the coordinator before launching a child. Its get_run view uses Observe mode and omits any parent command grant. Parent operations without task scope retain their normal run permissions.

Specialist model and tool-result events are published only in a transaction that rechecks parent and task authority. Expiry/revocation after a read therefore cannot publish a completed result or candidate evidence under stale task ownership. An interrupted read can remain unresolved until existing recovery examines it; scope loss never implies successful execution.

Write-enabled specialists now receive isolated snapshot-backed working trees. An immutable registered artifact captures the original project; completed task-owned journal entries overlay private edits. No private edit writes the original project. These are logical trees, not host directories or Git worktrees. Read-only tasks retain their original scoped reads. Snapshot creation and private read/list/write/create run in owned workers and recheck the exact saved task authority. Ordinary scoped host writes remain forbidden, and specialists never inherit a parent command grant.

Snapshots allow at most 4 MiB of source content per task and 32 MiB of snapshot artifacts per run, subject to existing file/path limits. Each task may change at most 16 files totaling 1 MiB. Complete file reads/writes are limited to 64 KiB. Artifact size/hash and completed overlay journal hashes are verified before review. Duplicate call IDs or idempotency keys are refused. Private writes commit atomically with their journal result, so process failure cannot leave an unjournaled host edit.

The review panel shows complete proposed diffs, checks current project bytes, and requires explicit authorization before integration. Conflicts require an explicit current/proposed choice with the observed current hash. The engine rechecks project bytes and applies approved content through frozen filesystem workers using compare-and-swap or exclusive creation. Saved authorization binds the task, exact bytes, local review lease and unique action ID. Partial integrations remain journaled. An unfinished integration intent blocks further writes until reconciliation; a completed write is recognized by its proposed hash and is not replayed. A known pre-effect failure permits a fresh explicit review with a new action ID.

This implements bounded user-reviewed integration. Specialist commands/tests, deletes, automatic merging, autonomous reviewers, task restart/adoption and private artifact retention controls remain open. Keeping current content is an explicit user decision, not proof that the rejected proposal's criteria were satisfied.
