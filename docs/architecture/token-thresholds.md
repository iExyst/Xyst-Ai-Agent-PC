# Reported-token stop thresholds

`POST /runs` accepts optional `max_total_tokens` (integer 1–100,000,000). CLI: `xaa run OBJECTIVE --model MODEL --max-total-tokens 20000`. Omission preserves the existing iteration/time-only behavior. The immutable configured threshold is persisted in the initial run event and returned under `limits`; older databases without that field retain no threshold, without changing schema version. To require a counted prompt-plus-output reservation before each request, set `pre_inference_token_reservations: true` in `POST /runs`, select **Reserve prompt and output tokens before each inference** in desktop Run limits, or pass `--reserve-tokens-before-inference` in the CLI. This requires `max_total_tokens` and exact LM Studio SDK support; count failures block before inference.

The coordinator checks durable reported prompt plus completion tokens across parent and specialist messages before inference, after saving a response and before each proposed tool. Equality permits the current response's tools/candidate but prevents another inference. Greater usage or unknown usage blocks work. Parent state becomes `blocked` with reason `token_budget_exhausted_or_unmeasured`; specialist failures retain the error type in their recorded outcome. Interrupted attempts and missing usage are not assumed free. Resume rechecks before restoring a candidate or replaying an incomplete sequence. No write is retried or refunded.

Reported-token budget runs without pre-inference reservations execute ready specialist assignments serially, claiming each just before execution, so an outstanding sibling request cannot be treated as free. With exact reservations enabled, up to two independent assignments run concurrently. Their model requests are serialized through budget admission and durable usage settlement; workspace and other non-inference work can overlap. Each inference still reserves its counted prompt and output allowance before HTTP, and the next request checks the settled response before admission. Runs without a token threshold retain two concurrent task slots. This increases specialist throughput without changing the provider's default single-inference policy or weakening the aggregate token gate.

Without pre-inference reservation mode, this is a measured stop threshold, **not a hard inference ceiling**. A request can cross the threshold before its usage arrives; the returned proposals are then blocked before execution. In reservation mode, prompt counts and the selected per-request output allowance are atomically held against the aggregate threshold before inference, including run-triggered diagnostics and specialists. Measured usage replaces the matching hold; interrupted/unmeasured requests keep their hold. Counting fails closed. This reduces overshoot risk but relies on LM Studio SDK/tokenizer correctness and does not protect against server misreporting or other LM Studio clients outside X.A.A.'s lock. Per-request output caps are available separately, as described below. The Phase 4 resource gate remains incomplete.

Original pre-diagnostic-accounting LM Studio acceptance: `uv run python scripts/token_threshold_diagnostic.py` used already-installed `qwen/qwen3.5-9b`, a threshold of 1 and a harmless read objective. Evidence `.acceptance/3a700b7c-668d-4a39-8695-acdcade2a756/` records 1,377 reported tokens, a read proposal, zero tool intents and unchanged fixture bytes/mtime. The model was unloaded afterward. This establishes post-response gating, not inference resource containment. Deterministic tests additionally cover missing usage, threshold equality, overage before a proposed write, shared specialist totals, interrupted requests, restart persistence and invalid settings.

## Per-request output caps

`POST /runs` additionally accepts optional `max_output_tokens` (integer 1–1,000,000); CLI `--max-output-tokens 512`. It persists with the initial run event and applies to parent requests and all specialists. It does not override total-token stop thresholds or grant a child extra allowance. Unconfigured runs preserve server defaults; diagnostics use a separate fixed 512-token output cap.

The provider maps this option to LM Studio's documented `max_tokens` chat-completions parameter. Capped streamed requests also send `stream_options.include_usage=true`. Assembled responses must contain consistent usage and report completion tokens no greater than the requested limit; missing usage and overage are explicit provider failures. The existing coordinator rejects length-truncated responses before executing tools, and incomplete streamed tool arguments remain non-executable. Provider enforcement is still required to contain actual generation; local verification can only reject a result after it arrives.

Official parameter reference: [LM Studio Chat Completions](https://lmstudio.ai/docs/developer/openai-compat/chat-completions), checked 2026-11-03. Live acceptance with `uv run python scripts/output_limit_diagnostic.py` is saved under `.acceptance/0bfe0c5b-2f4a-41ae-9a56-2f2088e7f8db/`: installed Qwen3.5 9B reports exactly one completion token for both normal and raw streamed requests, with `length` finish reasons; a separately executed coordinator request blocks with zero tool intents and unchanged fixture bytes. The stream probe inspects finish/usage fields only; it does not establish that a deliberately truncated answer can be assembled into a candidate. Wire-level deterministic tests cover both assembled modes, missing usage, reported overage and invalid limits. Specialist tests verify inherited option forwarding.

This bounds requested output per inference, not total prompt-plus-output use across a run. Hard aggregate ceilings and the Phase 4 resource gate remain incomplete. Desktop configuration and native acceptance are described below.

## Desktop controls and public contracts

Expand **Run limits** under New objective to set iteration/time bounds and optional token settings. Invalid or fractional values disable Start. New settings apply to newly submitted objectives; the Run resources section shows the saved active run's configuration independently of the editable form. It fetches measured input/output totals and the count of calls without usage, refreshes on inference/message/state events, and offers Retry token usage after a failed read. Failed reads are never displayed as zero consumption. The activity timeline explains output-cap and reported-threshold blocks.

The public `RunLimits` contract now includes both optional token settings. An API regression found that Pydantic previously omitted these extra stored fields from responses, despite correct engine enforcement; create/read/pause responses now explicitly preserve them. Specialist `TaskBudgets` remain a separate public type; optional task token settings are now implemented as described below. API, client types and generated OpenAPI match.

## Diagnostic accounting

The coordinator supplies an explicit request callback to the provider's capability diagnostic. Each actual request checks the reported-token threshold, persists `diagnostic.inference.started` with a unique ID before inference, and saves validated usage in `diagnostic.inference.completed` before another request or workspace proposal. Neither diagnostic messages nor private reasoning are saved in these events. Invalid/missing usage and interrupted requests remain unmeasured; a configured threshold fails closed. Completed diagnostics consume reported tokens but not the workspace iteration allowance. Cached capability checks make no new inference and add no charge. Historical runs cannot recover usage that was never recorded.

The callback is an optional provider interface parameter; standalone diagnostics do not create run-ledger events. The parent and explicit specialist-dispatch paths both use the accounting callback. Run output settings apply to task responses. Both standalone and run-triggered diagnostics now use a separate fixed 512-token output cap per request. The cap is recorded with each run-triggered start event. Length-truncated or filtered diagnostic responses never enable tools or populate the capability cache; run-triggered checks enter blocked state with `diagnostic_output_limit`. Unknown or over-cap usage is rejected by the same provider output verifier as task requests. This per-request output limit still does not bound prompt tokens or establish an aggregate inference ceiling.

The run blocks before the second diagnostic request and before any workspace model proposal or tool intent; fixture bytes and mtime are unchanged. The model was unloaded afterward. Deterministic tests cover each diagnostic boundary, missing/interrupted usage, reopen, cached checks and absence of private reasoning in the journal.

Capped native diagnostic acceptance: `.acceptance/14c21888-7894-4c6b-8cfb-1fb710fc71dd/` verifies both 512-token diagnostic request metadata and reported completion usage within that cap, plus the task cap, API/UI totals and no effects. ## Specialist allowances

Saved task definitions may specify `max_total_tokens` (reported prompt-plus-output threshold for that task) and `max_output_tokens` (per-request generated-token cap). Omitted task thresholds share the parent threshold; omitted task output caps inherit the run setting. Configured task output caps cannot exceed a configured parent cap. Runtime uses the smaller cap as an additional safeguard for old or inconsistent records. Task thresholds and caps cannot be increased by the specialist.

Plan creation checks that the sum of explicit task allowances fits the parent's latest unused reported-token threshold. Saved task allowances are not pre-consumed at plan time; in exact reservation mode, each request atomically checks both its task allowance and the shared parent ceiling before inference. In ordinary reported-threshold mode, a request can still overshoot before measured usage arrives. Readiness checks validate the saved graph against its original parent bounds, rather than subtracting spent tokens again and invalidating an already-saved plan. All requests still obey the shared parent threshold.

Specialist checks use only that assignment's durable inference/message events. Missing or interrupted usage fails closed when its own threshold is configured. Equality permits a current candidate/tool but blocks another inference. Over-threshold proposals are journaled as model messages, then blocked before tool intent. The blocked outcome keeps its error cause and prevents dependent execution. Existing records without task token settings retain the shared-run behavior. The plan view displays explicit allowances and inherited-setting labels.

Real source-engine acceptance: `uv run python scripts/task_token_diagnostic.py`. Inspect reports 538 tokens against its allowance of 1, blocks with zero tool intents and unchanged fixture bytes, and review is persistently blocked by its failed dependency without inference. Its configured output cap is 256, below the parent cap of 512; reported completion usage is 75. This is not model-generated planning or autonomous verification evidence. ## Native quota failure workflow

The plan API exposes only fixed `blocked_reason` codes, not private outcome JSON or worker authority. A specialist's own reported-token block displays a specific explanation; dependency blocks display that a prerequisite cannot proceed. Unknown blocked outcomes retain a generic explanation. After every specialist batch, dependency failures propagate transactionally to queued dependents, including concurrent batches. Explicit dispatch sets the parent to blocked when no ready task or reviewable candidate remains and a task is blocked/failed/cancelled.

Native model-generated acceptance: set `$env:XAA_NATIVE_TASK_QUOTA='1'` and run `node scripts/native_smoke.mjs`. It asks the installed Qwen3.5 9B model to discover a filename and save inspect/review tasks with a deliberately tiny inspect allowance of 1 and output cap 256. The parent uses threshold 50,000 and output cap 4,096 for planning. Only after saving the model-generated plan does the native UI dispatch inspect. Evidence `.acceptance/4cfdd3e8-75ee-4c36-ad1f-bc433365eb6a/` records a 652-token specialist response (142 generated), zero tool intents after dispatch, no dependent inference, unchanged fixture bytes, both tasks and parent blocked, and both explanations visible. Planning's earlier list/plan-save intents are preserved and are not counted as post-dispatch effects. The saved graph, binary digests, screenshot, quota report and graceful shutdown log are retained. This proves the intentional failure workflow; it does not establish hard inference containment or successful task completion.

## Context admission and output allowance

Known-context preflight now reserves the selected generated-token cap in addition to the existing conservative UTF-8 JSON/template estimate. Both normal and streamed entry points validate the cap before checking context and must reject an oversized request before posting to inference. History/tool-result pairs are not silently discarded. Without a selected cap, the existing heuristic remains; without known loaded context, this preflight cannot prove fit. It is deliberately conservative and may reject a prompt that an exact tokenizer would admit.

Live evidence `.acceptance/f9976ebf-3e45-442d-8ec2-0131abe33eaf/`: with context 16,384, normal and streamed requests selecting output 16,384 were rejected with zero inference HTTP requests; output 32 was admitted and the server reported 13 prompt plus 32 completion tokens. The optional reasoning-detail counter was 33, so that detail is not treated as an independently verified exact count; the existing ledger uses the consistent base usage fields. Reproduce with `uv run python scripts/context_preflight_diagnostic.py`.

A separate optional SDK probe matched four text/tool/history fixtures on the installed 9B model, but a 0.6B follow-up found SDK count timeouts and tool-history errors; see [tokenizer evaluation](../evaluations/tokenizer-parity.md). Durable count/output reservations are implemented for opt-in exact-context inference below. Ordinary inference still uses conservative admission, and broad model/tokenizer compatibility remains unverified. The native quota fixture now explicitly loads context 32,768 for its 4,096-output planning allowance; prior 16,384-context evidence remains historical.

The engine exposes the owned [tokenizer service](tokenizer-service.md) through an authenticated API and `xaa tokens`, with a bundled worker and credential/cancellation verification. Exact context count, durable hold and inference are atomic under the provider lock only when `XAA_EXACT_CONTEXT=1`; ordinary inference keeps conservative preflight. Existing reasoning-history fields and additional model templates need parity evaluation before broad enablement.

Durable token holds (2026-11-04): automatic exact-context mode now calls the coordinator's admission callback while retaining the provider lock, after successful context checking and before HTTP. `tokens.reserved` stores only inference ID, optional task ID, counted prompt tokens, output cap and their sum. Diagnostics, parent responses and specialists participate. Specialist attempts/replies now carry unique inference IDs; legacy journal rows remain readable. The reservation transaction checks the live parent lease, specialist lease when applicable, known reported usage, outstanding holds, the parent threshold and optional specialist allowance. Equality fits. Duplicate, answered or missing inference IDs reject. Counted prompt plus output must fit before prediction, even when existing reported usage alone is below the threshold.

A hold remains outstanding until a durable matching model/incomplete/diagnostic reply contains measured usage. Cancellation, crash or missing usage does not refund it. A measured reply implicitly substitutes actual usage for its hold, so the existing response transaction is the release boundary; there is no intervening release-before-save window. Historical unknown calls fail closed. This mode is opt-in and uses SDK-rendered counts; arbitrary models/templates, server misreporting, independently changing LM Studio clients and broad hard-budget parity are still unproven. Default mode retains the earlier reported-token threshold semantics. With exact reservations enabled, up to two independent specialist assignments may be active, while each inference waits for serialized durable budget admission and usage settlement. Without exact reservations, shared-threshold assignments are dispatched serially so parallel unmeasured usage cannot bypass the shared ceiling.
