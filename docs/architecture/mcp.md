# MCP integrations

Updated 2026-11-12. X.A.A. has stdio and Streamable HTTP client paths. This is not a claim of full Hermes MCP or plug-in parity.

## Static Agent Plugins package discovery

Portable `plugin.json` metadata follows the supported Agent Plugins v1 manifest rules: required schema/name and typed optional fields are checked locally, unknown top-level keys and a non-object `extensions` value are reported and ignored, and no schema is fetched at load time. Root `mcp.json` discovery validates its closed schema, checks stdio command/cwd path containment, validates HTTP headers and env references, and isolates invalid MCP configuration and server entries so discovered skills and valid siblings remain visible. Invalid individual skills are reported and skipped without hiding valid siblings or MCP servers. Unsupported SSE entries are reported and skipped. No client extension namespace is enabled. Stdio package records and launch parameters support package/data roots, reserved `PLUGIN_ROOT`/`PLUGIN_DATA`, bounded placeholder expansion, and path containment. Disconnected import re-reads a selected stdio or Streamable HTTP declaration from a fresh validated package scan, stores environment values and literal HTTP header values in the Windows Vault, and omits package paths and custom header mappings from API responses. Loopback HTTP integration verifies credential resolution and delivery. Local ZIP installation is a bounded authenticated operation. MCP imports record a bounded package-tree SHA-256 fingerprint; connection setup verifies it, and each tool call rechecks it, disconnecting on source change or loss. Legacy package integrations without a fingerprint must be removed and re-added after review. Explicit removal of an installed package is supported only under the app-managed package root, and is refused while an MCP integration references it; the owner confirms removal in the desktop. Removal preserves plugin data and imported immutable skill versions. Retained package data can be listed and deleted separately through authenticated managed-root operations and a second explicit desktop confirmation; deletion is refused while an integration references the package. Automatic package-script activation is unsupported; broad third-party compatibility remains incomplete.

The authenticated `POST /extensions/packages/discover` endpoint and desktop Agent plugin discovery panel inspect either one package directory or immediate child directories. Discovery bounds enumeration to 128 packages, 128 skills per package, 64 MCP servers, and 256 KiB per JSON/skill file. It validates package containment and manifests, rejects duplicate JSON keys, and reports per-package diagnostics. For each skill, it reads at most the first 16 KiB of `SKILL.md` and validates Agent Skills name/description/compatibility/metadata/allowed-tools frontmatter; the procedure body is not read during listing. A lowercase slug in `metadata.category` is retained in discovery, procedure versions and exported packages. YAML aliases are rejected. MCP summaries omit raw arguments, environment values, HTTP headers, and endpoint paths; stdio shows only the command basename, argument count, and environment variable names. Packaged HTTP endpoints are limited to HTTPS or loopback HTTP and reject URL credentials and fragments; query strings are retained as endpoint data.

Discovery does not execute package code. An explicit Import as candidate action reads a bounded UTF-8 `SKILL.md` up to 80 KiB and creates an inactive procedure candidate with source package/version, skill description, declared tools, manifest digest and content digest recorded in provenance. Exact declared tool names supported by X.A.A. map to candidate requirements; unknown names are retained and shown as unmapped. Requirements do not grant permissions: each trial remains bounded by the selected run's grants. Imported text stays untrusted and must go through the existing trial/evaluation/activation process. Markdown-linked local text resources are resolved within the skill directory, rejected on traversal or symlink escape, and bounded to 32 files, 64 KiB each and 1 MiB total. Each immutable procedure version stores resource bytes and digests; selected runs snapshot them, and the model can read only listed resources through `procedure_read_resource`, whose result is marked untrusted. Revisions retain resources when the editor submits no replacement set. Authenticated `GET /skills/{id}/versions/{version}/export` and the desktop Export action produce an Agent Plugins ZIP containing a plugin manifest, skill frontmatter/body and versioned linked text files; packages are rediscoverable and importable. Export preserves valid Agent Skills frontmatter or creates it for X.A.A.-authored procedures. MCP servers, credentials, evaluation history and local authority are not exported. Skill text is capped at 80 KiB for import/export; discovery still reads at most the first 16 KiB to inspect frontmatter. Export does not install packages, launch MCP processes, connect remote servers, or register tools. Full Agent Skills schema semantics, dependency/configuration translation, and script execution remain open. Bounded ZIP package installation is implemented and stays inert. An owner can import a package MCP entry as a disconnected integration, review it, then explicitly connect it from the MCP panel. `tests/integration/test_mcp_stdio.py` covers ZIP install, discovery/import, a real package-backed stdio server, default-deny permissions, an owner read grant and tool call, disconnect, and package removal. Tests cover round-trip resource packaging, frontmatter, candidate provenance/revision, traversal refusal, size refusal and authentication; symlink escape test may skip where Windows disallows symlink creation and must be exercised in CI.

Extraction rejects absolute/traversal paths, symlinks, encrypted entries, duplicate case-insensitive paths, file/count/expanded-size excesses and invalid manifests; existing package names are never overwritten. ## Configuration and lifecycle

The authenticated loopback API and desktop store a user-selected transport and endpoint or process command. Stdio uses an argument array and optional working directory; it never accepts a shell command string. Streamable HTTP uses an HTTPS endpoint, or plain HTTP only for loopback hosts. URL credentials, query strings and fragments are rejected. An optional bearer token is saved by its declared variable name through the OS credential store and is never returned in API responses.

Connecting is an explicit desktop action. The app initializes an MCP session, discovers tools, and keeps the transport alive for the app process lifetime. Connections are closed on disconnect or shutdown; the user reconnects after restart. Each connection has its own background owner task so AnyIO cancellation scopes stay in their creating task. Calls on one server are serialized. Stdio and non-OAuth initialization are bounded to 15 seconds; HTTP OAuth setup allows up to 302 seconds for browser consent. Calls are bounded to 45 seconds, listings to 256 tools/eight pages, input schemas to 128 KiB, and results to 256 KiB. Streamable HTTP uses the official SDK client, same-origin redirect policy, certificate verification, and an authenticated request header when a token is configured.

Disconnect and app shutdown keep each live connection registered until its close operation succeeds. If shutdown fails, the integration remains present, its tools are withheld, and authenticated disconnect/delete requests return an error; deletion also preserves its credentials so the owner can retry shutdown. OAuth sign-in clearing follows the same confirmed-disconnect rule. Manager shutdown uses the same close path instead of discarding connection records on errors. This protects against reporting revocation while a transport may still be live; it does not yet provide durable recovery of a failed transport shutdown across app termination.

When an HTTP MCP endpoint returns a supported OAuth challenge, the pinned SDK performs authorization-code + PKCE using a loopback callback bound to `127.0.0.1` on a random port and an unpredictable callback path. The desktop connect action waits up to five minutes for the owner to complete sign-in in their browser. Dynamic client registration metadata and access/refresh tokens are stored separately per MCP server in Windows Credential Manager. The token profile also records an absolute expiry; on reconnect, an expired token is refreshed before use, and older token profiles without an expiry are conservatively refreshed or reauthorized. The desktop shows whether tokens are saved and provides “Clear sign-in,” which disconnects the server and removes both vault entries. A configured static bearer token takes precedence and skips OAuth. Local loopback integration verifies resource/authorization metadata discovery, registration, state callback, PKCE verifier exchange, vault persistence, refresh after expiry, older-format migration, denial without token storage, and reconnect without another browser flow. Native Windows desktop acceptance with a bundled engine additionally verifies browser callback, PKCE exchange, vault persistence, reconnect and sign-in clearing against a local fixture; see [`../releases/native-acceptance.md`](../releases/native-acceptance.md). Hosted Windows installer run [42800363137](https://github.com/iExyst/Xyst-Ai-Agent-PC/actions/runs/42800363137) passed the release-stage acceptance. Third-party OAuth provider interoperability remains open.

The desktop provides explicit owner actions to list and read MCP resources and to list and preview MCP prompts. Resource catalogs are limited to eight pages, 256 entries and a 256 KiB serialized response; a read accepts only a URI from that connected server's most recently listed catalog. Text and base64 blob content are bounded to 256 KiB in total per read. Prompt catalogs use the same page, entry and response bounds; previews require the prompt to be in the most recently listed catalog, accept only declared arguments, cap each argument at 8 KiB and all arguments at 32 KiB. Prompt previews retain text, image, audio, embedded-resource and resource-link content types within a 256 KiB serialized response. The panel renders preview output as escaped text under an "Untrusted MCP prompt preview" label. Owner resource inspections are returned only to the desktop and never enter model context. Prompt previews also stay owner-only by default. After previewing, the owner may explicitly add a text-only prompt as JSON-formatted untrusted reference data to the editable objective field; the desktop enforces the 10,000-character objective limit and asks the owner to review it before starting the run. Images, audio, embedded resources and resource links remain inspection-only. This does not automatically select a prompt or grant MCP tools. Resource templates can be listed as owner-only metadata with the same eight-page, 256-entry and 256 KiB catalog limits. An owner can supply all advertised variables and read one resource through RFC 6570 expansion; only URIs produced from the current advertised template catalog are accepted, and the per-connection expanded-URI cache is capped at 256. Expansion uses the pinned `uritemplate` dependency; its BSD-3-Clause and Apache-2.0 alternatives are recorded in the provisional dependency notices. Template content uses the same 256 KiB untrusted read path and is never added to model context. A server without the requested capability gets a clear inspection error. Automatic prompt selection remains unimplemented; owner-confirmed text-only prompt inclusion is supported as described above. Modern sampling on protocol 2026-07-28 uses the SDK `InputRequiredResult` multi-round-trip flow and `Client.call_tool` driver; legacy server-initiated sampling remains supported when a server is explicitly configured for the legacy handshake. Automatic negotiation remains the default. Both routes use the same explicit per-run server grant and callback. The standalone server-initiated `sampling/createMessage` method is deprecated in the modern MCP protocol; the multi-round-trip `Sample` resolver is its current replacement. During an approved connected tool call, the callback is bound to the owning run, journals bounded request/completion/failure events, uses the run's selected provider/model and shared iteration/token budget, passes only untrusted text with no workspace or conversation history and no tools, and requires bounded text output with measured usage. An interrupted or unmeasured sample fails closed and is never retried. The SDK high-level `Client.call_tool` owns the modern input-required retry loop, so each sampling answer is reused on subsequent rounds instead of triggering duplicate inference. Legacy mode remains for servers that require the older back-channel. On protocol 2026-07-28, the connection owner uses the SDK `Client.listen` stream for explicitly selected resource URIs; older negotiated versions use the legacy `resources/subscribe` path. `notifications/resources/updated` events are accepted only for the exact subscribed URI, tagged untrusted, and placed in a per-connection queue capped at 128. The desktop displays notices only after the owner selects “Check for server updates”; it never fetches changed resource content automatically. Queue overflow replaces pending notices with `resync_required` so the owner can refresh and inspect manually. The same legacy notification path and overflow behavior pass local stdio and loopback Streamable HTTP fixtures; broad third-party interoperability remains unverified.

Schema 29 adds the per-server MCP protocol mode and migrates existing records to `auto`; older transport and endpoint columns are also added without changing existing stdio records. A new or changed MCP tool schema resets its permission to `none`.

## Permissions and trust

Discovered tools are namespaced by server ID. Their JSON schemas are validated, external `$ref` targets are rejected, and a digest covers schema, description, title, and annotations. The user can classify each tool as disabled, read, or write. Read tools can be offered to runs; write tools are only offered when the user separately selects them for that run. Tool intents and results are journaled, and results are labelled `untrusted_mcp_output`. Server metadata and output are untrusted data.

A connection-owner task that exits immediately after discovery is rejected before its server and tools are published as connected. The owner receives the sanitized connection error and must explicitly connect again. After a live stdio transport loss, the in-flight call is recorded as `unknown_outcome`, the dead session is cleared and the owner can reconnect manually. Permissions survive only while the tool schema digest still matches; ambiguous calls are never replayed. Automatic retry is intentionally not performed. A disconnect before tool execution returns a known `not_connected` status after recording a completed result for the proposed call; it does not leave an unresolved intent or fail the run. Cancelling an in-flight write closes its connection, records `cancelled_unknown_outcome`, and leaves no unresolved intent. A timeout, transport failure, server-reported error, or output overflow during a write is journaled as `unknown_outcome` and is never retried automatically because a remote side effect may have happened. The system prompt asks the model to reconcile externally before proposing another write.

The coordinator blocks immediately after an MCP write returns `unknown_outcome`; it does not ask the model to continue first. Any later calls in the same model response are journaled as not started, keeping the replayable tool-call sequence complete. The active run view provides an explicit check for ambiguous MCP writes without exposing their arguments or response content. After inspecting the external system, the owner can record that the effect happened or did not happen. This decision is audited and replaces the ambiguous tool result used on a later run continuation; it never replays the original call. Reconciliation is refused while the run has a live worker lease. The owner then explicitly resumes the blocked run.

Specialists may inherit an exact qualified MCP tool name only when the saved MCP registry classifies that tool as `read`. The task plan cannot grant a write-classified tool; the specialist exposes only connected, schema-matched read tools named in its permission scope. Before calling the server it journals the qualified name, arguments, read classification and schema digest under the task/model-call identity. A completed result is attached from that journal after worker loss; an unfinished read is sealed as `interrupted_read` with no assumed content and is never replayed by recovery. This delegation does not expose MCP write tools to specialists.

Configured stdio processes run with the user's process privileges. HTTP endpoints receive only the configured bearer token and user-authorized requests. Neither transport adds OS/container isolation for MCP servers.
