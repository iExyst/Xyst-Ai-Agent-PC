# MCP integrations

Updated 2026-11-05. X.A.A. has initial stdio and Streamable HTTP client paths. This is not a claim of full Hermes MCP or plug-in parity.

## Static Agent Plugins package discovery

The authenticated `POST /extensions/packages/discover` endpoint and desktop Agent plugin discovery panel inspect either one package directory or immediate child directories. Discovery bounds enumeration to 128 packages, 128 skills per package, 64 MCP servers, and 256 KiB per JSON/skill file. It validates package containment and manifests, rejects duplicate JSON keys, and reports per-package diagnostics. For each skill, it reads at most the first 16 KiB of `SKILL.md` and validates Agent Skills name/description/compatibility/metadata/allowed-tools frontmatter; the procedure body is not read during listing. A lowercase slug in `metadata.category` is retained in discovery, procedure versions and exported packages. YAML aliases are rejected. MCP summaries omit raw arguments, environment values, HTTP headers, and endpoint paths; stdio shows only the command basename, argument count, and environment variable names. HTTP endpoints are limited to HTTPS or loopback HTTP and reject URL credentials, query and fragment.

Discovery does not execute package code. An explicit Import as candidate action reads a bounded UTF-8 `SKILL.md` up to 80 KiB and creates an inactive procedure candidate with source package/version, skill description, declared tools, manifest digest and content digest recorded in provenance. Exact declared tool names supported by X.A.A. map to candidate requirements; unknown names are retained and shown as unmapped. Requirements do not grant permissions: each trial remains bounded by the selected run's grants. Imported text stays untrusted and must go through the existing trial/evaluation/activation process. Markdown-linked local text resources are resolved within the skill directory, rejected on traversal or symlink escape, and bounded to 32 files, 64 KiB each and 1 MiB total. Each immutable procedure version stores resource bytes and digests; selected runs snapshot them, and the model can read only listed resources through `procedure_read_resource`, whose result is marked untrusted. Revisions retain resources when the editor submits no replacement set. Authenticated `GET /skills/{id}/versions/{version}/export` and the desktop Export action produce an Agent Plugins ZIP containing a plugin manifest, skill frontmatter/body and versioned linked text files; packages are rediscoverable and importable. Export preserves valid Agent Skills frontmatter or creates it for X.A.A.-authored procedures. MCP servers, credentials, evaluation history and local authority are not exported. Skill text is capped at 80 KiB for import/export; discovery still reads at most the first 16 KiB to inspect frontmatter. Export does not install packages, launch MCP processes, connect remote servers, or register tools. Full Agent Skills schema semantics, dependency/configuration translation, script execution, install/activation and MCP package lifecycle remain open. Tests cover round-trip resource packaging, frontmatter, candidate provenance/revision, traversal refusal, size refusal and authentication; symlink escape test may skip where Windows disallows symlink creation and must be exercised in CI.

## Configuration and lifecycle

The authenticated loopback API and desktop store a user-selected transport and endpoint or process command. Stdio uses an argument array and optional working directory; it never accepts a shell command string. Streamable HTTP uses an HTTPS endpoint, or plain HTTP only for loopback hosts. URL credentials, query strings and fragments are rejected. An optional bearer token is saved by its declared variable name through the OS credential store and is never returned in API responses.

Connecting is an explicit desktop action. The app initializes an MCP session, discovers tools, and keeps the transport alive for the app process lifetime. Connections are closed on disconnect or shutdown; the user reconnects after restart. Each connection has its own background owner task so AnyIO cancellation scopes stay in their creating task. Calls on one server are serialized. Initialization is bounded to 15 seconds, calls to 45 seconds, listings to 256 tools/eight pages, input schemas to 128 KiB, and results to 256 KiB. Streamable HTTP uses the official SDK client, same-origin redirect policy, certificate verification, and an authenticated request header when a token is configured.

Schema 15 adds the transport and endpoint columns while preserving older stdio records as `stdio`. A new or changed MCP tool schema resets its permission to `none`.

## Permissions and trust

Discovered tools are namespaced by server ID. Their JSON schemas are validated, external `$ref` targets are rejected, and a digest covers schema, description, title, and annotations. The user can classify each tool as disabled, read, or write. Read tools can be offered to runs; write tools are only offered when the user separately selects them for that run. Tool intents and results are journaled, and results are labelled `untrusted_mcp_output`. Server metadata and output are untrusted data.

A disconnect before execution returns a known `not_connected` status after recording a completed result for the proposed call; it does not leave an unresolved intent or fail the run. Cancelling an in-flight write closes its connection, records `cancelled_unknown_outcome`, and leaves no unresolved intent. A timeout, transport failure, server-reported error, or output overflow during a write is journaled as `unknown_outcome` and is never retried automatically because a remote side effect may have happened. The system prompt asks the model to reconcile externally before proposing another write.

The coordinator blocks immediately after an MCP write returns `unknown_outcome`; it does not ask the model to continue first. Any later calls in the same model response are journaled as not started, keeping the replayable tool-call sequence complete. The active run view provides an explicit check for ambiguous MCP writes without exposing their arguments or response content. After inspecting the external system, the owner can record that the effect happened or did not happen. This decision is audited and replaces the ambiguous tool result used on a later run continuation; it never replays the original call. Reconciliation is refused while the run has a live worker lease. The owner then explicitly resumes the blocked run.

Specialists may inherit an exact qualified MCP tool name only when the saved MCP registry classifies that tool as `read`. The task plan cannot grant a write-classified tool; the specialist exposes only connected, schema-matched read tools named in its permission scope. Before calling the server it journals the qualified name, arguments, read classification and schema digest under the task/model-call identity. A completed result is attached from that journal after worker loss; an unfinished read is sealed as `interrupted_read` with no assumed content and is never replayed by recovery. This delegation does not expose MCP write tools to specialists.

Configured stdio processes run with the user's process privileges. HTTP endpoints receive only the configured bearer token and user-authorized requests. Neither transport adds OS/container isolation for MCP servers.
