# Exclusive workspace file creation

`workspace_create_file` is available only to workspace-mode runs. It accepts a plain relative path and UTF-8 content capped at 64 KiB. Parent directories must already exist; no directory creation, destination overwrite, links or junction traversal is supported. Paths reject traversal, drive prefixes, alternate streams, device aliases and ambiguous trailing dots/spaces. Depth is capped at 32 components.

The Windows backend pins the workspace directory and every descendant directory with handles that deny delete sharing. It opens each child relative to its parent handle, inspects reparse attributes, and verifies its actual handle path. The leaf uses `NtCreateFile` with the parent as `RootDirectory`, `FILE_CREATE`, no sharing and `FILE_NON_DIRECTORY_FILE`. This binds creation to the verified directory rather than resolving a second absolute pathname. See [Microsoft's NtCreateFile reference](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/nf-ntifs-ntcreatefile). Other platforms fail closed until a verified backend is implemented.

The coordinator persists the proposal and intended action before entering the exclusive create operation. A definite failure before creation (including a collision or denied parent) produces durable `effect: not_started` feedback. Once creation succeeds, stream setup, lease checks, writes, flushes or result-persistence failures leave the intent unresolved. The `tool.executing` event follows successful handle creation; an interrupted process may therefore leave an empty file even without that event. Recovery relies on the durable intent, not the presence of an execution event.

Automatic recovery opens the destination with the existing exclusive reader and verifies containment. Exact desired bytes confirm the requested effect and record a reconciled result without rewriting. An absent or different destination stays unresolved and blocks automatic continuation. Recovery never recreates or overwrites it automatically.

While blocked, the authenticated desktop recovery panel can list uncertain direct workspace writes using paths and hashes without exposing file contents. An owner may confirm that a create did not apply only after removing the partial file and leaving its destination absent; an edit may be confirmed not applied only after restoring the saved previous SHA-256. A separate filesystem worker rechecks those conditions, records the original tool call as failed with `not_applied_after_review`, and does not replay it. The owner can then explicitly resume the run; any new write requires a new model proposal and still goes through normal preconditions. This confirms the current destination state, not whether another process observed a partial file before it was removed.

Verification covers nested creation, collision preservation, simultaneous creators, rename denial while parent handles are held, a real external Windows junction, unsafe paths, observe-mode denial, and injected fsync failure with matching/missing/conflicting recovery. Real-model native create/read/final-review and real worker kills after creation/before content and after fsync/before result passed. A fresh-process owner-recovery acceptance also removes an incomplete create only after inspection, then resolves it through the frozen worker without repeating the write (`../.acceptance/929ca6cf-0a06-4fa4-8282-60a151cc892f/owner-reconciliation.json`). Worker-isolated filesystem timeouts, Linux support and native streaming creation acceptance remain open.
