# Exclusive workspace file creation

`workspace_create_file` is available only to workspace-mode runs. It accepts a plain relative path and UTF-8 content capped at 64 KiB. Parent directories must already exist; no directory creation, destination overwrite, links or junction traversal is supported. Paths reject traversal, drive prefixes, alternate streams, device aliases and ambiguous trailing dots/spaces. Depth is capped at 32 components.

The Windows backend pins the workspace directory and every descendant directory with handles that deny delete sharing. It opens each child relative to its parent handle, inspects reparse attributes, and verifies its actual handle path. The leaf uses `NtCreateFile` with the parent as `RootDirectory`, `FILE_CREATE`, no sharing and `FILE_NON_DIRECTORY_FILE`. This binds creation to the verified directory rather than resolving a second absolute pathname. See [Microsoft's NtCreateFile reference](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/nf-ntifs-ntcreatefile). Other platforms fail closed until a verified backend is implemented.

The coordinator persists the proposal and intended action before entering the exclusive create operation. A definite failure before creation (including a collision or denied parent) produces durable `effect: not_started` feedback. Once creation succeeds, stream setup, lease checks, writes, flushes or result-persistence failures leave the intent unresolved. The `tool.executing` event follows successful handle creation; an interrupted process may therefore leave an empty file even without that event. Recovery relies on the durable intent, not the presence of an execution event.

Recovery opens the destination with the existing exclusive reader and verifies containment. Exact desired bytes confirm the requested effect and record a reconciled result without rewriting. An absent or different destination stays unresolved and blocks automatic continuation. Recovery never recreates or overwrites it automatically. This confirms destination contents, not which process created a matching file.

Verification covers nested creation, collision preservation, simultaneous creators, rename denial while parent handles are held, a real external Windows junction, unsafe paths, observe-mode denial, and injected fsync failure with matching/missing/conflicting recovery. Real-model native create/read/final-review and real worker kills after creation/before content and after fsync/before result also passed; evidence is recorded in `docs/progress.md`. Worker-isolated filesystem timeouts, Linux support and native streaming creation acceptance remain open.
