# Procedure Python dependencies

## Scope

Python dependency declarations in imported Agent Plugin and Hermes procedures are untrusted metadata. The existing check reads installed distribution metadata without importing packages. Installation must remain a separate, owner-initiated action. A requirement declaration, model response, procedure activation, or command grant never installs a package by itself.

This design supports Python wheels only. Other managers, requested extras, direct URLs, and source distributions stay explicitly unsupported until they have their own bounded installer and provenance rules.

## Immutable environment identity

An environment belongs to one exact procedure identity and version, source-content digest, target WSL distribution, Python implementation/version/ABI, and normalized PEP 508 requirement set. The authenticated WSL readiness probe now captures the target interpreter's marker environment and ordered compatible wheel tags from a temporary private venv. Its canonical manifest and all downloaded wheel bytes receive SHA-256 digests. The environment key is the digest of that complete input; updates create a new environment and never mutate an existing one.

`PyPIWheelResolver` now turns the complete imported requirement set and server-probed target into a pending candidate lock. It uses PEP 691 wheel records and PEP 658 `core-metadata`, filters by ordered target tags and `Requires-Python`, evaluates markers against the WSL target, and performs bounded backtracking over transitive `Requires-Dist` constraints. It accepts only binary wheels with SHA-256 and size records and rejects unsupported extras, direct references, yanked files, and candidates without published metadata. Resolution is bounded by time, projects, files, candidate versions, metadata requests, package count, and total wheel size. The desktop exposes this as an owner-initiated action after a successful target probe. Metadata from PyPI remains an untrusted proposal until `PyPIWheelAcquirer` downloads the exact wheel files and `verify_locked_wheel_bytes` confirms the recorded hashes, `METADATA`, and `WHEEL` tags. A mismatch blocks approval.

The metadata parser, dependency solver, and exact-wheel acquisition now run in Windows AppContainer workers with networking denied. The resolver worker receives normalized requirements, target markers/tags, and the immutable procedure identity. The acquisition worker receives only the saved lock and writes exact wheel files to its bounded private workspace. A stdio broker in the engine performs TLS-verified, redirect-disabled HTTPS requests only to `pypi.org` and `files.pythonhosted.org`; it allows at most 512 requests, 2 MiB project pages, 1 MiB metadata records, and 352 MiB aggregate response bytes during acquisition. Wheel bodies move in pull-based 512 KiB frames, so the engine does not buffer an aggregate wheelhouse. AppContainer process-tree, memory, CPU, private-storage, 120-second runtime, protocol-output and workspace limits apply. The engine independently verifies the exact workspace file set, wheel hashes and archive metadata, then streams files into an atomic content-addressed wheelhouse commit. Approval rechecks committed wheel paths and metadata without loading the entire wheelhouse into memory. Deterministic Windows integration acceptances exercise source and frozen workers against an in-memory mock index without public PyPI access.

An explicit install action is now available only for a saved, approved lock with its verified wheelhouse. The Windows engine maps that exact application-owned directory into the selected WSL distribution, and the root-side manager copies and rechecks every wheel before installation. `pip` receives only those wheel paths with `--isolated --no-index --no-cache-dir --no-compile --only-binary=:all: --no-deps` inside a no-network Bubblewrap namespace. The WSL systemd unit caps runtime at 120 seconds, memory at 768 MiB, CPU at 50%, and tasks at 32; temporary storage is a 32 MiB tmpfs. The installer rejects wheel archives with unsafe paths, links, special files, excessive members, or more than 256 MiB aggregate expanded content. It validates the resulting regular-file tree against a 640 MiB and 20,000-file cap, transfers ownership to root, seals files read-only, and publishes a canonical manifest only after installation succeeds. The environment digest is its immutable directory identity. Status rehashes the installed tree; exact-digest removal is supported by the manager. A local WSL acceptance verified offline install of a transitive two-wheel fixture, idempotent reinstall, integrity status, and removal without public PyPI access.

The desktop and authenticated API expose the owner install and exact-digest removal actions and persist the WSL tree receipt. At run creation, X.A.A. requires an explicit choice when multiple approved installed environments match the selected Python-bearing procedure version and WSL grant; it automatically selects the sole match. The immutable procedure event saves the selected digest/tree hash, and each command intent inherits that binding rather than taking it from model arguments. Before launch, the root WSL manager rehashes the installed tree, verifies the host WSL Python version still matches the venv's recorded version, and mounts the matching venv read-only at `/opt/xaa/procedure-python`, placing its interpreter first on PATH. Commands remain network-denied and receive the selected project snapshot separately. Real WSL acceptances verify fixture imports from the mount, rejected writes, active-use removal refusal followed by successful removal after cleanup, and isolation between two installed environments. Focused storage/API tests and the Skills browser flow verify selection and lifecycle behavior. A complete real imported-procedure model run remains incomplete and is deferred until the end per the user's testing preference; imported-procedure dependency execution remains **partial**.

## Preparation and installation boundaries

1. The production resolver obtains binary wheels from public PyPI only, using normal TLS verification. Metadata parsing, solving, and exact-wheel acquisition run in unprivileged, no-network AppContainer workers; the engine acts as a narrow, bounded PyPI network broker. Source distributions are refused so package build hooks never run during resolution.
2. The resolver records every wheel's normalized project name, version, compatible tag, size, SHA-256, and normalized `Requires-Dist` entries parsed from its wheel metadata. The owner reviews this exact lock before installation. The installer must independently compare recorded metadata to the bytes whose hash matches the lock.
3. Installation consumes only the approved lock's verified wheelhouse with networking disabled, `--no-index`, binary-only rules, and dependencies disabled because every resolved wheel is supplied directly. It runs as the unprivileged sandbox identity with system files read-only and a single writable environment target. No project files or procedure scripts are present during installation.
4. The manager validates the completed target contains only bounded regular files/directories, rejects links and special files, computes a content digest, transfers ownership to root, and seals the immutable target read-only. The manifest and status are published only after installation succeeds. Failed or interrupted preparations remain unavailable and can be reconciled by exact environment identity; exact-digest removal is implemented in the manager.

The persistent cache is application-owned WSL data, outside `/usr`, `/opt` system packages, user site-packages, and project workspaces. The offline installed environment is mounted read-only only for a command whose saved authorization names the matching procedure version and environment digest. The matching virtual-environment interpreter is selected for that command; the host interpreter and system Python remain unchanged. The command profile continues denying networking and exposing only the selected private workspace, runtime, and explicitly authorized dependency environment.

## Lifecycle and authority

- Discovery and dependency readiness remain advisory and do not install, import, or grant authority.
- The desktop requires an explicit owner action after showing the complete resolved lock. Approval is tied to one immutable procedure version and target environment.
- Revision creates a separate candidate and cannot silently reuse a prior environment. A previously approved environment may be selected again only when its full identity matches.
- Rollback selects an older immutable environment. It does not rewrite package files in place.
- Removal is a separate owner action, addresses only one exact environment digest, and refuses while a command still holds that environment.
- Logs and API responses expose package identifiers and versions, not credentials, environment values, or local installation paths.

## Acceptance gates

Use a local package index fixture with a small binary wheel and a transitive dependency. Verify resolver backtracking, exact and ranged constraints, tag preference, `Requires-Python`, target markers, yanked-file refusal, metadata-hash checks, and bounded project/candidate/search limits. Then verify lock normalization and hashes, `Requires-Dist` extraction against wheel bytes, dependency graph closure, owner review before installation, offline installation, and successful import only from the exact selected environment inside the network-denied WSL sandbox. The current `scripts/wsl_procedure_environment_acceptance.py` verifies offline install, idempotence, integrity, imports from the read-only venv mount, denied writes, and exact removal. Separate WSL acceptances verify concurrent environment separation and active-use removal refusal/cleanup. Unit and browser coverage verify exact selection among multiple matching environments and binding of the saved digest/tree hash into command intents. Still required: end-to-end execution of a real imported procedure, interrupted install reconciliation under process termination, immutable revision and rollback acceptance, and preservation of the system interpreter, project bytes, credentials, and unrelated environments. No live model or public package service is required for these deterministic acceptance gates.

Until the remaining acceptance gates pass, imported Python dependencies are only partially supported for installation and execution.
