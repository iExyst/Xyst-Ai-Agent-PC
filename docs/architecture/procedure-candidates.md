# Versioned procedure candidates

The first skills workflow is a user-authored candidate library, available in the desktop under Reusable procedures and through the authenticated local API. It supports creation, inspection, immutable revisions, historical version export and deletion of a candidate and all its versions. Explicitly selected versions can now be included in evaluation trial runs as described below. There is no automatic retrieval or promotion. Activation, deprecation, rollback and routine active-skill reuse remain unimplemented; this does not meet the complete Phase 5 gate.

Each version stores procedure text, named/versioned tool dependencies, declared workspace read/write permissions, creation time and application-generated candidate/user provenance. Dependencies are declarations and may name unavailable tools; saving a draft does not verify support or grant permissions. User input cannot set lifecycle state, active version or evaluation evidence. Procedure names belong to the library entry; revising the title does not preserve an independent title for older text versions.

The existing schema-3 skills tables store these records; no migration is required. A transaction creates each version with its parent entry. Revisions require expected_version and use BEGIN IMMEDIATE, so concurrent editors cannot overwrite a newer version. Existing version text/manifests are never updated. Limits are 100 entries, 128 versions per entry, 16384 UTF-8 bytes per version, 32 unique tool dependency names and the two current workspace permissions. Deletion cascades to all versions. SQLite backup/restore preserves entries and versions.

API: GET/POST /skills; GET/DELETE /skills/{id}; POST /skills/{id}/versions; GET /skills/{id}/versions/{version}. All routes require the same local bearer authentication. Duplicate names and stale revisions return 409; missing entries/versions return 404 and invalid manifests return 422. Typed request/response schemas are exported to the desktop. Downloads contain only the selected saved version and entry name, without engine credentials.

Seven engine cases cover immutable revision history, a real two-connection concurrent edit, backup restoration, cascade deletion, bounds, rejected self-activation fields and authenticated API behavior. Malicious stored procedure text creates no run or tool call. The browser workflow creates, revises, inspects a historical version, verifies historical editing is disabled, downloads that version and deletes the entry. Full suite: 273 passed with the existing Starlette/httpx warning; seven browser checks pass (one live check skipped), seven client checks pass; Ruff/format, strict Pyright, TypeScript and contracts pass.

## Explicit versioned trial runs

CreateRunRequest accepts optional procedure_trial with skill_id and version. The desktop offers Select version for trial run, shows the unverified selection before submission and allows removal. Selection clears after successful submission. Creating a run resolves the candidate version and snapshots its content/manifest in the same SQLite transaction as run.queued. Missing dependencies/versions, omitted required permissions and requirements exceeding the selected mode/workspace reject before any run is committed. The initial supported trial dependencies are version-1 workspace file/list/search/edit tools; unavailable declared dependencies remain valid drafts but cannot be trialed. Requirements are minimum dependencies, not additional grants or a replacement for run policy.

The procedure.selected event contains the frozen version and SHA-256 of its text/tool/permission manifest. The public run record includes its name, ID, version and digest. Parent context loads the saved snapshot, checks its digest and clearly labels it unverified procedure data subordinate to current objective, tools, permissions and budgets. Children do not receive it automatically. Later library revisions/deletion do not change existing run snapshots. Context admission/counting includes this text; the procedure cannot grant a permission, increase a budget, enable an unsupported tool or mark itself evaluated/active.

## Explicit evaluation records

An authenticated user can now record an evaluation of a specific procedure version. GET /skills/{id}/versions/{version}/trials lists up to 50 recent completed matching trials for the editor picker. POST /skills/{id}/versions/{version}/evaluations requires two to ten distinct run IDs, distinct representative case descriptions, one to twenty explicit criteria with every index confirmed exactly once, a rationale, and the expected number of prior evaluation records. The transaction rejects stale review counts, uncompleted/unreviewed runs, wrong procedure versions/digests, missing loaded-context markers and unresolved tool actions. It stores the manifest digest, case descriptions, run revision/final-review sequence, criteria, rationale, UTC time and local-user actor. At most 32 records are supported per version. The application verifies evidence linkage and completion; the reviewer judges substantive quality and representativeness.

The desktop picker supports two cases, displays saved evaluation evidence and requires confirmation again when cases or criteria change. Evaluation changes the version's evidence state to evaluated and, when reviewing the latest version, the entry summary state. It never sets active_version. New revisions reset the entry to candidate while preserving all older manifests and evaluation records. Candidate/evaluated entries can still be explicitly trialed, exported or deleted. Automatic reviewer decisions, activation/deprecation and rollback remain future work. No procedure text is allowed to submit this user-only API operation.

Nine evaluation tests cover exact completed-trial linkage, stale review rejection, candidate reset after revision, preserved historical evidence/backup restore, wrong-version/pending/missing trial rejection, duplicate cases and criteria acknowledgment, authentication and inactive state. Ruff/format, strict engine/diagnostic Pyright, TypeScript and contracts pass.
