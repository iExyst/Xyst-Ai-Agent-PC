# Versioned procedure candidates

The procedure library is available in the desktop under Reusable procedures and through the authenticated local API. Candidates may be user-authored or created by a model only when the local user explicitly grants procedure drafting for that run. It supports creation, inspection, immutable revisions, historical version export and deletion of a candidate and all its versions. Explicitly selected versions can be included in evaluation trial runs. Explicit activation, deprecation, rollback and selected active-version reuse are available. The desktop can also rank up to five currently active versions from name/description/category overlap with the current objective; it shows matched terms, and the user must inspect the exact active version and select it separately. This suggestion path never loads procedure instructions, selects a run version, or promotes a candidate. It is bounded lexical discovery assistance, not semantic retrieval or full Hermes skill parity.

Each version stores procedure text, named/versioned tool dependencies, declared workspace read/write permissions, creation time and application-generated candidate provenance. Dependencies are declarations and may name unavailable tools; saving a draft does not verify support or grant permissions. User and model draft inputs cannot set lifecycle state, active version or evaluation evidence. Procedure names belong to the library entry; revising the title does not preserve an independent title for older text versions.

## Explicitly authorized model drafts

Run creation accepts `allow_procedure_drafting`, default false. The desktop exposes this as a separate next-run checkbox and consumes the grant as soon as submission starts, including when the request fails or its outcome is ambiguous. A granted run exposes `procedure_draft`; the storage layer rechecks the persisted grant under the run lease, permits at most three candidates per run, and records the source run/tool-call identity in the immutable version provenance. Candidate creation, its version, tool intent/result and audit events commit in one SQLite transaction. A duplicate name, exhausted library or injected storage failure leaves no candidate and no unresolved tool call.

Model drafts are create-only through `procedure_draft`. They remain `candidate`, have no active version and contain no evaluation evidence until a user inspects and separately trials/evaluates them. This tool cannot revise entries, activate, evaluate, select or execute a candidate. `tests/unit/test_procedure_drafting.py` covers grant enforcement, coordinator tool visibility, provenance, inactive lifecycle and transaction rollback; `tests/browser/objective.spec.ts` checks the grant is sent and consumed on submission. Linked resource manifests use the existing bounded `SkillDraft` validation; package review and runtime readiness remain separate.

## Explicitly authorized model revisions

Run creation accepts `allow_procedure_revision`, default false, and requires an explicitly selected latest procedure version. The desktop permission is separate from candidate creation and is consumed at submission, including on failed or ambiguous requests. A granted run exposes `procedure_revise` only for the selected procedure ID and version. The tool accepts either a full text rewrite or an exact `old_string`/`new_string` replacement on the main procedure body; repeated matches require explicit `replace_all`. Linked files cannot be changed. Name, dependencies, permissions, metadata, and linked resources are copied unchanged. Storage rechecks the durable user grant, selection, live run lease, and expected latest version under `BEGIN IMMEDIATE`; it writes the new immutable version, completed tool call, and audit events in one transaction. A stale revision, invalid target, or injected insert failure creates no partial version or unresolved call.

Every model revision starts as `candidate` with empty evaluations. An existing active pointer remains unchanged. The user must inspect, trial, evaluate, and separately activate or roll back through the existing lifecycle controls. `tests/unit/test_procedure_revision.py` covers authorization, target/version binding, active-pointer preservation, manifest-field rejection, linked-resource preservation, conflict rollback, API persistence, and coordinator tool visibility/execution; `tests/browser/skills.spec.ts` verifies that only the latest selected version can be granted and that failed or successful submissions consume consent. A live Qwen3.5 9B coordinator acceptance revised a selected version while retaining its prior content and permissions: `.acceptance/live-procedure-revision-b44ba3f63dcd43bab2de3c4739f78f3e/report.json`. Full rewrites and exact main-body replacements are implemented.

## Separately authorized linked-resource revisions

Run creation accepts `allow_procedure_resource_revision`, default false, and requires the explicitly selected latest version. This grant is separate from main-text revision; a run may select only one of the two revision types. The UI consumes it at submission, including ambiguous failures. A granted run exposes `procedure_resource_revise` only for the selected procedure ID/version. One call creates or replaces one normalized relative UTF-8 linked resource (64 KiB per file, with existing 32-file/1 MiB package limits). Storage rechecks grant, selected version, live lease, call identity and current latest version inside `BEGIN IMMEDIATE`, preserves the main text, tools, permissions, metadata, all other resources and active pointer, then saves the unevaluated candidate, tool result and audit events atomically. Resources are untrusted text; script execution, deletion, batching, and multi-file edits remain unsupported.

`tests/unit/test_procedure_revision.py` verifies replacement and creation, path traversal rejection, package preservation, separate-grant enforcement, API persistence and coordinator schema/execution. `tests/browser/skills.spec.ts` checks mutually exclusive grants, latest-version selection and consumption after submission. A live Qwen3.5 9B coordinator acceptance called `procedure_resource_revise` exactly once, replaced `references/guide.md`, preserved the main text and original bytes, created an inactive unevaluated version, and left no workspace effects or unresolved calls: `.acceptance/live-procedure-resource-revision-3254264d548b45ecbb20593524c2b094/report.json`. The version remains inactive/unevaluated and goes through the existing user trial/evaluation/lifecycle controls.

Linked resource removal has a distinct `allow_procedure_resource_removal` grant and `procedure_resource_remove` tool. It removes exactly one normalized path from a new candidate version; the prior version and other package fields remain unchanged. Tests cover consent exclusivity, path validation, missing paths, API persistence, candidate state, and the coordinator tool round trip. This is not claimed as live-model verified; multi-file writes, batching, broader manager semantics and non-text assets remain unsupported.

The existing schema-3 skills tables store these records; no migration is required. A transaction creates each version with its parent entry. Revisions require expected_version and use BEGIN IMMEDIATE, so concurrent editors cannot overwrite a newer version. Existing version text/manifests are never updated. Limits are 100 entries, 128 versions per entry, 81,920 UTF-8 bytes per version, 32 unique tool dependency names and the two current workspace permissions. Selected runs start with procedure metadata and retrieve the exact immutable body only through `procedure_view`. Deletion cascades to all versions. SQLite backup/restore preserves entries and versions.

API: GET/POST /skills; GET/DELETE /skills/{id}; POST /skills/{id}/versions; GET /skills/{id}/versions/{version}. All routes require the same local bearer authentication. Duplicate names and stale revisions return 409; missing entries/versions return 404 and invalid manifests return 422. Typed request/response schemas are exported to the desktop. Downloads contain only the selected saved version and entry name, without engine credentials.

Seven engine cases cover immutable revision history, a real two-connection concurrent edit, backup restoration, cascade deletion, bounds, rejected self-activation fields and authenticated API behavior. Malicious stored procedure text creates no run or tool call. The browser workflow creates, revises, inspects a historical version, verifies historical editing is disabled, downloads that version and deletes the entry. ## Explicit versioned trial runs

CreateRunRequest accepts optional procedure_trial with skill_id and version. The desktop offers Select version for trial run, shows the unverified selection before submission and allows removal. Selection clears after successful submission. Creating a run resolves the candidate version and snapshots its content/manifest in the same SQLite transaction as run.queued. Missing dependencies/versions, omitted required permissions and requirements exceeding the selected mode/workspace reject before any run is committed. The initial supported trial dependencies are version-1 workspace file/list/search/edit tools; unavailable declared dependencies remain valid drafts but cannot be trialed. Requirements are minimum dependencies, not additional grants or a replacement for run policy.

The procedure.selected event contains the frozen version and SHA-256 of its text/tool/permission manifest. The public run record includes its name, ID, version and digest. Parent context loads the saved snapshot, checks its digest and clearly labels it unverified procedure data subordinate to current objective, tools, permissions and budgets. Children do not receive it automatically. Later library revisions/deletion do not change existing run snapshots. Context admission/counting includes this text; the procedure cannot grant a permission, increase a budget, enable an unsupported tool or mark itself evaluated/active.

Eight targeted cases cover immutable selection after revision/deletion, permission/tool/version rejection with no orphan queued run, authenticated API selection, observe-mode write denial despite procedure text, and corrupt-snapshot rejection before workspace inference. ## Explicit evaluation records

An authenticated user can now record an evaluation of a specific procedure version. GET /skills/{id}/versions/{version}/trials lists up to 50 recent completed matching trials for the editor picker. POST /skills/{id}/versions/{version}/evaluations requires two to ten distinct run IDs, distinct representative case descriptions, one to twenty explicit criteria with every index confirmed exactly once, a rationale, and the expected number of prior evaluation records. The transaction rejects stale review counts, uncompleted/unreviewed runs, wrong procedure versions/digests, missing loaded-context markers and unresolved tool actions. It stores the manifest digest, case descriptions, run revision/final-review sequence, criteria, rationale, UTC time and local-user actor. At most 32 records are supported per version. The application verifies evidence linkage and completion; the reviewer judges substantive quality and representativeness.

The desktop picker supports two cases, displays saved evaluation evidence and requires confirmation again when cases or criteria change. Evaluation changes the version's evidence state to evaluated and, when reviewing the latest version, the entry summary state. It never sets active_version. New revisions reset the entry to candidate while preserving all older manifests and evaluation records. Candidate/evaluated entries can still be explicitly trialed, exported or deleted. Automatic reviewer decisions, activation/deprecation and rollback remain future work. No procedure text is allowed to submit this user-only API operation.

## Explicit activation, reuse and rollback

POST /skills/{id}/lifecycle accepts activate, rollback or deprecate plus rationale, expected active/latest versions and expected lifecycle revision. GET on that path returns bounded audit history. Activation/upgrade and rollback require saved evaluation evidence matching the target manifest digest. Rollback requires an older evaluated version. Transactions compare the monotonic lifecycle revision as well as the active/latest pointers, preventing stale decisions even after an upgrade/rollback returns to the same pointer. The current limit is 256 lifecycle decisions per entry. Audit records contain actor, time, from/to versions, digest and rationale in the schema-4 table.

Creating a draft or evaluating a newer version preserves an existing active pointer. Evaluation never activates a version. Active entries must be deprecated before deletion. Deprecation clears the pointer and blocks all new selections; explicitly creating a new draft revives a candidate, or an explicit activation can restore an evaluated version. Existing queued/running snapshots remain unchanged by rollback, deprecation or library deletion. These actions do not stop a run or broaden its permissions.

The existing run-selection field procedure_trial now supports purpose=evaluation_trial (default) or active_use. Active use requires the exact currently active version at queue time and still checks declared dependencies against workspace/mode. The selected purpose is stored in the frozen snapshot and public run metadata. Procedure context stays subordinate to run policy, and past evaluations do not verify a new run. The desktop shows latest and active versions separately, exposes rationale-based lifecycle controls and audit history, and lets the user explicitly select an active version for the next run. There is no automatic skill retrieval or silent promotion. Children do not automatically inherit this parent procedure context.

### Opt-in active procedure suggestions

`GET /skills` now includes the description/category metadata for the active version, or the latest version when an entry has no active pointer. The desktop's explicit "Find matching active procedures" action checks only active entries and token overlap against the current objective. A suggestion requires at least two distinctive metadata-token matches, or an exact procedure name; up to five results display their matched terms. Candidate/evaluated-only drafts cannot appear. The current objective changing clears old suggestions. Selecting a result opens the exact active version in the existing editor; only the separate "Select active procedure for next run" action creates a run selection. At queue time, the existing transaction still verifies that this version remains active and that its tool requirements fit the selected workspace/mode. No procedure body or untrusted instruction is read during suggestion ranking.
