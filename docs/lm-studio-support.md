# LM Studio support matrix

Checked on 2026-10-27 against the official [REST API overview](https://lmstudio.ai/docs/developer/rest), [Responses API](https://lmstudio.ai/docs/developer/openai-compat/responses), [MCP API guide](https://lmstudio.ai/docs/developer/core/mcp), and [server settings guide](https://lmstudio.ai/docs/developer/core/server/settings), plus the installed Windows application and `llmster` 0.0.25-1 in Ubuntu 24.04 WSL. The installed Windows app reports version **0.4.26.0** (file version **0.4.26+4**). `GET http://127.0.0.1:1234/api/v1/models` succeeded and returned 45 models. The WSL headless daemon also served models and inference. The available inventory contains loaded state, model size, quantization, maximum context, and declared vision/tool-use capabilities.

A bounded live Xyst CLI native chat request to an already-loaded model returned the requested marker and token statistics with `store: false`; no model was loaded for the check. The packaged Windows CLI repeated this smoke and handled token-like model output: redaction was applied, the response stayed valid JSON, and the token-like marker was absent. A regression test covers the response-redaction bug that previously could invalidate response JSON.

LM Studio recommends its native REST API v1 for new integrations; the docs identify it as released in 0.4.0. Xyst uses native v1 where it covers the feature and compatible endpoints where they provide custom tool calls or embeddings. Endpoint behavior is version-dependent; this matrix records what is implemented and what is still pending in Xyst.

The native `GET /api/v1/models` inventory and OpenAI-compatible `GET /v1/models` inference list can expose different model identifiers. Before using a loaded instance ID for tool-enabled inference, Xyst now checks that exact ID against `/v1/models`. If the exact instance ID is absent, Xyst uses the base model key only when exactly one instance is loaded and that base key is listed; otherwise it returns an actionable error before sending the prompt. Explicitly selected instance IDs are never silently replaced.

### Native MCP integrations for direct LM Studio chat

On 2026-10-27, the exact packaged Windows CLI sent an authenticated, read-only GitHub MCP request through LM Studio using the existing `github` / `personal-token` OS-vault credential. `issue_read` returned live metadata for issue #1 in `iExyst/xyst-agent-validation`; the credential value and issue body were not included in the saved proof. The request used `https://api.githubcopilot.com/mcp/readonly` and `allowed_tools: ["issue_read"]`. See sanitized evidence. Configured `mcp.json` plugins remain unverified because the installed file has no servers configured.

`xyst lm ask` and `xyst lm stream` accept `--integration-file <path>` with a JSON array of LM Studio plugin and ephemeral-MCP integration definitions. Secret HTTP header values are represented by credential-vault references in `credential_headers`, then resolved only for the request. The file is capped at 64 KiB; remote MCP URLs must use HTTPS (HTTP is accepted for loopback only). A configured plugin can be selected by its `mcp/<server-label>` ID, optionally limiting `allowed_tools`. Users can save definitions under `integrations.lmStudio.nativeChat.integrations` and enable automatic inclusion under `integrations.lmStudio.nativeChat.enabled`; desktop Settings exposes the same fields. An explicit `--integration-file` overrides the saved set for one command. This direct native chat path is separate from Xyst's policy-managed agent tool loop. It requires Xyst network, integration, and external-action capabilities; it is unavailable when per-tool external-action approval is enabled because LM Studio executes the tools outside Xyst's approval loop. LM Studio server settings must allow the selected configured/per-request MCP type, and LM Studio may require authentication for `mcp.json` plugins. See [LM Studio chat integration documentation](https://lmstudio.ai/docs/developer/rest/chat) and [MCP server settings](https://lmstudio.ai/docs/developer/core/server/settings).

Example `lm-integrations.json`:

```json
[
  { "type": "plugin", "id": "mcp/playwright", "allowed_tools": ["browser_navigate"] },
  {
    "type": "ephemeral_mcp",
    "server_label": "private-search",
    "server_url": "https://mcp.example.test/mcp",
    "allowed_tools": ["lookup"],
    "credential_headers": { "Authorization": { "service": "private-search", "name": "api-token" } }
  }
]
```

Set the credential with `xyst credential set private-search api-token`, then call `xyst lm ask <model> --integration-file lm-integrations.json <prompt>`.

### OpenAI-compatible Responses API

Use `xyst lm responses request.json` or add `--stream` for SSE output. The file contains the documented request body, with `model` and `input` required. Xyst accepts the common Responses fields (`instructions`, `max_output_tokens`, `metadata`, `parallel_tool_calls`, `previous_response_id`, `prompt`, `reasoning`, `store`, `temperature`, `text`, `tool_choice`, `tools`, `top_p`, `truncation`, and `user`) and rejects unknown top-level fields. The file is limited to 1 MB. Since the API stores state when requested, save the returned response ID alongside any client state that needs to resume; mission objectives and task history remain in Xyst's SQLite store.

Function tools are sent as declarations and any returned function calls remain data for the caller; use `xyst agent run` when Xyst must validate and execute local tools through its shared policy and journal. Remote MCP tools use the Responses API `type: "mcp"` shape (`server_label`, `server_url`, optional `allowed_tools`). If authentication headers are needed, use the Xyst extension `credential_headers` with OS-vault references, for example `{ "Authorization": { "service": "private-search", "name": "api-token" } }`; raw `headers` values are rejected. MCP execution happens inside LM Studio, so it requires network, integrations, and external-action access, and Xyst rejects it when per-tool external-action approval is enabled. LM Studio's server-side Remote MCP permission must also be enabled. Stream output reports text deltas directly or one JSON event per line with `--json`; an incomplete response exits with code 2.

Example request:

```json
{
  "model": "publisher/model",
  "input": "Look up one documentation fact",
  "reasoning": { "effort": "low" },
  "tools": [
    {
      "type": "mcp",
      "server_label": "private-search",
      "server_url": "https://mcp.example.test/mcp",
      "allowed_tools": ["lookup"],
      "credential_headers": {
        "Authorization": { "service": "private-search", "name": "api-token" }
      }
    }
  ]
}
```

### Model load controls in Xyst

The local model view exposes REST load controls and idle-unload TTL for local LLM and decision models. Agent settings independently control automatic loading, automatic unloading, and the idle TTL. On LM Studio's default local API server (loopback port 1234), Xyst preloads an unloaded model when automatic loading is enabled; its automatic TTL uses `lms load --ttl`. Custom-port loopback and remote servers use documented JIT loading and receive the per-request TTL when automatic unloading is enabled. With loading disabled, Xyst stops before inference if the selected model is not already loaded. A model already loaded outside Xyst is not unloaded or reconfigured, and Xyst does not change server-wide JIT/auto-evict preferences. Its **Estimate resources without loading** action invokes the local CLI estimate with the selected context and GPU placement; this CLI path targets the default server on port 1234. Leave any field at **LM default** to omit it from the request and preserve LM Studio's own defaults. After loading, the view reads `loaded_instances[].config` back from inventory so it reports the applied values rather than echoing only the requested form. Embedding models expose context length only because the documented REST API does not list LLM evaluation settings for embeddings.

CLI example:

```sh
xyst lm load publisher/model --context-length 8192 --eval-batch-size 512 --flash-attention --no-offload-kv-cache-to-gpu
xyst lm load publisher/model --context-length 8192 --ttl 900
xyst lm estimate publisher/model --context-length 8192 --gpu max
xyst lm load publisher/model --gpu 0.5 --context-length 8192
xyst lm load publisher/main --speculative-draft-model publisher/draft --speculative-draft-max-tokens 8
xyst lm load publisher/main --speculative-draft-mtp
```

The previous positional context form (`xyst lm load publisher/model 8192`) remains supported. GPU layer offload and speculative decoding use the installed lms CLI for local servers. GPU ratio and Draft MTP can be selected independently; simple speculative decoding lets the user choose another installed LLM as the draft and adjust token/probability limits. LM Studio may reject incompatible main/draft model pairs at load time; Xyst does not independently predict compatibility. CLI load settings can be combined with context length, but not with REST-only batch, attention, expert, or KV settings; the desktop blocks those combinations. LM Studio does not report actual GPU layer allocation in model inventory, so the UI labels the value as the last requested CLI target rather than a measured effective allocation.
